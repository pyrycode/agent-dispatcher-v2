# #71 — `src/salvage/draft-pr.ts` salvage draft-PR opener

Third file under `src/salvage/`. Thin orchestrator over two injected GitHub clients that pins the **load-bearing order** for a `max_turns` salvage: apply `error:max_turns_salvaged` to the source issue first, then create the draft PR. The order is the entire reason this module exists — anywhere the salvage flow opens a PR, it goes through `openSalvageDraftPr` so the ordering can't be re-derived (and re-broken) at the call site.

## Exports

- `SALVAGE_LABEL = "error:max_turns_salvaged"` — the literal label name. Exported so the dispatcher's pre-dispatch gate and any future predicate audit can reference one source of truth.
- `SalvageDraftPrDeps` — `{ labels: Pick<GitHubLabelsClient, "addLabel">; pr: Pick<GitHubPrClient, "createPr"> }`. Structurally-minimal seam — declares at the type level that the function needs exactly two methods.
- `OpenSalvageDraftPrInput` — `{ issueNumber, title, body, head, base }`. No `draft` knob; salvage PRs are always drafts.
- `openSalvageDraftPr(deps, input): Promise<number>` — awaits `addLabel(input.issueNumber, SALVAGE_LABEL)`, then awaits `createPr({ ...input, draft: true })`, returns `pr.number`. No try/catch anywhere.

## Why the ordering matters

V1 lesson, 2026-05-03: the safety primitive (label on the source issue) must precede the artifact (PR). The label is what the next dispatcher cycle keys on to skip re-dispatch. If the PR exists but the label doesn't (because `addLabel` failed transiently after `createPr` succeeded), the loop sees an unlabeled issue and an open PR on `feature/N` — it can treat the PR as normally ready (code-review / auto-merge path) or re-dispatch a developer against the same branch. Both are wrong; the operator wanted to triage the half-finished draft.

Inverting the order rules this out: if labelling fails, **no PR exists yet** and the next cycle sees the original `max_turns` state, which is recoverable. If labelling succeeds but PR creation fails, the issue is blocked from re-dispatch and an operator notices a stuck issue — also recoverable. The only unrecoverable case ("PR exists, label doesn't") is structurally impossible here.

## No try/catch — load-bearing

`addLabel` throws on transport failure ([#36](36.md)); this module deliberately does not catch. The throw IS the safety net — it stops execution before `createPr` runs. Wrapping in try/catch would defeat the deterministic-safety-net property the whole salvage flow depends on (`CLAUDE.md` § Belt-and-suspenders). `createPr` also propagates its throws verbatim ([#41](41.md)); recovery (rolling back the label, logging, alerting) belongs at the orchestrator where the broader context lives, not here.

Test 3 (`addLabel throws → createPr never invoked; the throw rethrows verbatim`) pins this: the assertion `pr.calls.length === 0` after a thrown `addLabel` is the regression backstop. A future refactor that wraps `addLabel` in try/catch breaks that assertion. The test comment explicitly notes this also covers AC bullet 5 ("no try/catch swallowing") so a future reader doesn't add a redundant sixth test.

## Label goes on the source issue, not the PR

The dispatcher's selection / re-dispatch logic keys on **issue** labels. The PR is a downstream artifact. A later orchestrator ticket may also label the PR for code-review-side filtering — that's a separate decision, separate evidence threshold ([deferred — see Open Question 1 in the spec](../../specs/architecture/71-salvage-draft-pr.md)).

The function takes `issueNumber` as explicit input — it does not assume `feature/N` ↔ issue `N`. The caller knows which issue is being salvaged.

## Patterns established

- **Structural fakes over routing-table transport mocks when the seam is tiny.** This module touches two methods. Tests inject `{ addLabel }` and `{ createPr }` objects that satisfy `Pick<...>` of the full client interfaces. The routing-table transport mock (used by `test/github/labels.test.ts` and `test/github/pr.test.ts`) tests the clients themselves — adding two layers of indirection (transport call sequence, GraphQL/REST string matching) to a test that only cares about ordering would obscure the assertion. Same posture as #69's injected `GateRunner`: size the seam to what the function actually uses, mock at that seam.
- **Order-pin tests use a shared `events: string[]` array.** Both fakes push their name (`"label"`, `"create"`) into a shared array; the test asserts `events.toEqual(["label", "create"])`. Catches a future refactor that runs them in `Promise.all` (non-deterministic interleaving) or swaps the order. Cheaper and clearer than spying on call timestamps.
- **`Pick<ClientInterface, "method">` for DI surfaces.** When a module needs one method off a multi-method client, type the dependency as `Pick<...>` of just that method. Documents the structural minimum at the type level; lets tests inject one-method objects without satisfying the rest of the interface. Mirrors `SalvageDraftPrDeps`'s `labels: Pick<GitHubLabelsClient, "addLabel">` shape.
- **Named-constant export for a load-bearing string literal.** `SALVAGE_LABEL = "error:max_turns_salvaged"` is exported because the same string will appear at the dispatcher's pre-dispatch gate (when it lands). One source of truth prevents drift between producer and consumer. Lives in this file (the producer) rather than `src/pipeline/transitions.ts` because the salvage label is an artifact-class label produced exclusively here — the transition table tracks status-class labels mutated by pure decision functions. Hoist only when a second producer exists.
- **Deps-first, input-second argument order.** `(deps, input)` matches the broader DI convention — deps are the wiring, bound once by the orchestrator; input is the per-call data. The orchestrator will likely bind deps once and call this with many inputs.
- **Bare `number` return until a second field is needed.** AC says "returns PR number"; the function returns `pr.number`, not the full `PrInfo`. Widening the return shape is non-breaking; narrowing isn't. Same posture as #41's `enableAutoMerge` returning `void`.
