# #60 — `src/loop/runReworkRouting.ts` per-cycle rework-routing

Fourth and final maintenance routine under `src/loop/`. Lands `runReworkRouting(deps) → Promise<void>`: each dispatch cycle, every item carrying a `needs-rework:<agent>` label has its stale `ready:* / wip:* / error:*` labels stripped and its project Status moved back to the target agent's column. Completes the four-runner template alongside `runDoneCleanup` (#57), `runClosedSweep` (#58), and `runAutoMerge` (#59).

The decision is pure: `decideReworkRouting(labels) → { target, stripLabels }` plus the new `targetColumnForAgent(agent) → Column` — both in `src/pipeline/routing.ts`. The runner is the I/O edge that applies them.

## Surface

- `runReworkRouting(deps)` — async, no return value. Sequential `for...of` over items.
- `ReworkRoutingDeps = { listItems, removeLabel, setItemStatus }` — narrow ports. Not the whole `GitHubProjectClient` / `GitHubLabelsClient`.
- `ReworkRoutingItem = { itemId, issueNumber, status, labels }` — minimal projection of `ProjectItem`. **Both** id fields are required: `removeLabel` keys on `issueNumber`, `setItemStatus` keys on the GraphQL project-item `itemId` (a `PVTI_*` node id). Mixing the two is the one easy mistake.
- `targetColumnForAgent(agent: Agent) → Column` — new pure export from `src/pipeline/routing.ts`. Backed by an unexported `Record<Agent, Column>` so adding a member to `Agent` (derived from `Label`) is a TS error here rather than a silent miss-route.

## Behavior

Per item, in order:

1. `decideReworkRouting(item.labels)` — if `target === null`, skip the rest of the iteration (no status read, no mutator call).
2. For each name in `stripLabels`, `await removeLabel(item.issueNumber, name)`. The set is computed by the pure decision; the runner does NOT branch on label prefixes itself.
3. If `item.status !== targetColumnForAgent(target)`, `await setItemStatus(item.itemId, targetColumn)`.

The triggering `needs-rework:*` label is intentionally NOT stripped — `decideReworkRouting` already excludes it from `stripLabels`, and the target agent's run is what consumes (and eventually replaces) it.

## Why these contracts

### `targetColumnForAgent` lives in `src/pipeline/routing.ts`, not in the runner

The mapping `po → Backlog`, `architect → In Architecture`, `developer → In Development`, `code-review → In Code Review` is implicit in the rework rows of `TRANSITIONS`. Two reasons to lift it into a named pure export rather than `switch` inside the runner:

- **Purity rule.** CLAUDE.md § "Pure functions in `src/pipeline/`" — agent→column is a pipeline decision; the loop runner is an I/O orchestrator. A `switch` in the runner would smuggle pipeline logic into the I/O layer.
- **Exhaustiveness.** `Record<Agent, Column>` forces a TS error the moment `Agent` widens (e.g. if a future ticket adds `needs-rework:documentation` to `Label`). A `switch` with a fall-through default would silently miss-route.

`AGENT_TO_COLUMN` is module-private; only the function is exported. Same encapsulation as the existing `REWORK_PREFIX` / `STRIP_PREFIXES` constants in the file.

### Two id fields on `ReworkRoutingItem`

`runDoneCleanup`'s item carries only `issueNumber`. This runner needs `itemId` too because `setItemStatus` is keyed on the project-item GraphQL node id, not the issue number. Both fields are already on the production `ProjectItem` (`id` and `issueNumber`), so the eventual wiring is still a one-liner. Do NOT widen `DoneCleanupItem` to add `itemId` — separate ports, separate shapes, narrow per consumer.

### Strip-then-status ordering

The runner strips labels before setting status. Reasoning:

- Reads "clear stale state, then move the card", matching how a future reader thinks.
- Resumable on partial failure: if `setItemStatus` throws after a successful strip, the next cycle re-routes — `needs-rework:*` is still there, `stripLabels` is now empty (no-op), and the status check fires `setItemStatus` again.
- Reverse order is also correct (the in-loop status check keys on the snapshot from `listItems`, not a re-read). The chosen order is convention, not correctness.

### Three idempotency layers

1. **No `needs-rework:*` on the item.** `decideReworkRouting` returns `target: null` — `continue` short-circuits the iteration. Zero mutator calls.
2. **Already in target column, no stale labels.** `stripLabels` is empty (no strip loop iterations) and `item.status === targetColumn` (status check false). Zero mutator calls.
3. **`removeLabel` is GET-then-PUT-only-if-present** (`src/github/labels.ts`). A repeated strip costs one GET, no PUT.

The AC explicitly pins layers 1 and 2 as observable via call counts in the test fakes.

### No try/catch

`listItems`, `removeLabel`, `setItemStatus` propagate transport errors verbatim. Matches the no-catch posture across `src/github/*` and the three sibling runners. The future dispatcher loop decides abort / continue / circuit-break.

### `decideReworkRouting`'s `as Agent` cast is not re-guarded here

Routing.ts:36 casts `label.slice("needs-rework:".length)` to `Agent` after the prefix match. A malformed `needs-rework:bogus` label would slip through as `target: "bogus"` and `AGENT_TO_COLUMN["bogus"]` would yield `undefined`. The runner does NOT defend against this — it's a `decideReworkRouting` contract concern, and adding a guard here would be exactly the kind of unobserved-failure defense CLAUDE.md flags. If it ever happens, `setItemStatus(itemId, undefined)` throws downstream and surfaces the bad data.

## Patterns established by this ticket

- **Pure agent→column mapping belongs in `src/pipeline/routing.ts`, not the runner.** Any future I/O routine that needs to translate `Agent` to `Column` imports `targetColumnForAgent` rather than open-coding the switch. Adding a new `Agent` widens automatically through the `Label`-derived type and surfaces as a TS error at the `Record<Agent, Column>` literal — single source of truth, structurally enforced.
- **The four-runner template is complete and stable.** `runDoneCleanup` (#57), `runClosedSweep` (#58), `runAutoMerge` (#59), `runReworkRouting` (#60) all share: narrow `Deps` interface (one port per I/O concern), minimal item projection (only the fields actually consumed), sequential `for…of`, no `try/catch`, no retry, no `AbortSignal`, pure decision imported from `src/pipeline/`. Future maintenance routines follow this template; deviations need justification.
- **Per-consumer item shapes, not a shared `LoopItem`.** Each runner declares its own `*Item` interface with exactly the fields it reads. `ReworkRoutingItem` adds `itemId` that `DoneCleanupItem` does not need; don't unify. The cost of duplication is one interface per file; the cost of a shared shape is coupled runners.
- **Pure exhaustive maps over `switch` for agent/label/column translations.** `Record<Agent, Column>` is load-bearing typing. Bare `Record<string, Column>` or a `switch` with a default defeats the point — the whole reason for the new export is that a future widening of `Agent` must fail loudly at this site.

## Lessons learned

- **`setItemStatus` keys on `itemId` (`PVTI_*`), `removeLabel` keys on `issueNumber`.** Project-item GraphQL node id vs. REST issue number are different identifiers — the production `ProjectItem` exposes both as `id` and `issueNumber`. New runners that touch project Status need `itemId` in their item projection; runners that only touch labels do not. Mixing them is the one easy mistake; the type system catches it only if the ports declare distinct parameter types (they do, but a `string` typo would still compile).
- **Don't re-derive strip-prefix logic at the I/O edge.** The temptation is to write `labels.filter(l => l.startsWith("ready:") || …)` in the runner. Resist: `decideReworkRouting` already returns the exact strip set with the triggering `needs-rework:*` deliberately excluded. Duplicating the filter at the call site (a) violates CLAUDE.md § "`decideLabelDelta` is the only place labels mutate" by introducing a second strip authority, and (b) would silently mask a regression if the pure function's exclusion ever broke.
- **`documentation` is not in `Agent`.** `Agent` is `ExtractAgent<Label>` — there is no `needs-rework:documentation` label, so `documentation` is correctly absent from `AGENT_TO_COLUMN`. Don't pre-emptively add a `documentation: "In Documentation"` row "just in case"; that's defending against an unobserved failure mode. If the label is ever added, `Agent` widens automatically and TS flags the missing key.
