# #53 — `src/loop/cycle.ts` `runCycle`

v2's heartbeat. Stitches every pure-pipeline decision and every I/O surface that has landed so far into one tick. First file under `src/loop/` that composes the four sibling runners (`runDoneCleanup`, `runClosedSweep`, `runAutoMerge`, `runReworkRouting`) end-to-end and is the only call site where both arms of CLAUDE.md's throughput equation are observable on the same tick.

## Exports

- `CycleSnapshot` — `{ readonly items: readonly SelectionItem[]; readonly inFlightCount: number }`. One fetch, one array; the I/O layer derives `inFlightCount` from the same query.
- `RunCycleDeps` — narrow port: `fetchSnapshot`, `dispatchAgent(tuple)`, `applyAdvance(decision)`, four `run*` thunks, `sleep(ms)`. No `gh` / `git` / `fs` imports anywhere in this file.
- `RunCycleConfig` — `{ maxConcurrent, pollIntervalMs, drain: AbortSignal }`.
- `runCycle(deps, config): Promise<void>` — the loop. `while (!drain.aborted) { tick; if (drain.aborted) break; sleep; }`.

## Tick contract (fixed order)

1. `fetchSnapshot` — one snapshot per tick.
2. `selectDispatches({ items }, capacity)` where `capacity = max(0, maxConcurrent - inFlightCount)`.
3. `Promise.allSettled(tuples.map(dispatchAgent))` — true parallel start, sequential await, **one rejection does not abort the tick or siblings**.
4. `decideAutoAdvance({ items }, inFlightCount, maxConcurrent)` → sequential `applyAdvance` per decision.
5. `runDoneCleanup → runClosedSweep → runAutoMerge → runReworkRouting`, sequential. Unconditional — runs even on an empty board.

The settled array from step 3 is **ignored**: per-dispatch logging / error labels / salvage live inside `deps.dispatchAgent`, not here. `runCycle` has one concern — tick orchestration.

## The throughput equation, observable on one tick

```
actual_wip = min(
  selectDispatches.cap,
  decideAutoAdvance.backlog_cap,
  blocker_chain,
  MANUAL_ADVANCE_GATES,
)
```

Both gates receive the same effective capacity. `selectDispatches` takes `capacity` directly (the caller pre-subtracts `inFlightCount`); `decideAutoAdvance` does the subtraction internally (`Math.max(0, maxConcurrent - inFlightCount)`). The v1 incident (2026-05-08, `decideAutoAdvance` hardcoded WIP=1 while `selectDispatches` honoured `maxConcurrent`) is structurally impossible in v2 — bumping `maxConcurrent` reaches both arms through the same config field, and the binding-cap test pins the invariant.

Dispatch and auto-advance are **not in tension**: `selectDispatches` walks non-Backlog columns, `decideAutoAdvance` walks only Backlog. Both can fully use the capacity on the same tick — selected items dispatch this tick, advanced items dispatch next tick once their column is selectable. Allocation order is irrelevant because `actual_wip` is bounded by `min(...)`, not the sum.

## Drain is an `AbortSignal`, checked at tick boundaries only

The launcher (future ticket, `src/dispatch-bin.ts`) wires `process.on("SIGTERM", () => controller.abort())`. `runCycle` does not register signal handlers — it only knows about `config.drain`. Checked twice per loop iteration: at the `while` head and after `tick()` resolves, so a drain raised mid-sleep skips the next tick.

**Mid-tick: no check.** Once `tick()` starts, it runs to completion — `Promise.allSettled` awaits every in-flight dispatch, then `applyAdvance` calls and the four reconcile thunks run sequentially. This is the intended semantics: "stop accepting new work, finish in-flight dispatches, exit cleanly." `dispatchAgent` is not passed the signal — wiring cancellation into salvage / worktree-cleanup is out of scope.

## Reconcile via thunks, not direct imports

`runCycle` never imports `runDoneCleanup` / `runClosedSweep` / `runAutoMerge` / `runReworkRouting`. Each is a pre-bound thunk in `deps`. Reason: the four runners each have their own narrow deps (`DoneCleanupDeps`, etc.). Importing them here would force `RunCycleDeps` to carry the union of `listItems` / `removeLabel` / `setItemStatus` / `listPrsForItem` / `mergePr` — leaking plumbing into a layer that orchestrates nothing but tick order. The launcher constructs each runner's deps once at startup: `runDoneCleanup: () => runDoneCleanup(doneCleanupDeps)`. Tests stub each thunk independently.

A `reconcile()` aggregator was rejected by the spec. Wrapping the four runners adds no shared state and no shared deps; it would also create a fifth label-mutation surface, which CLAUDE.md "`decideLabelDelta` is the only place labels mutate" forbids.

## `Promise.allSettled`, not `Promise.all`

`Promise.all` rejects on the first rejection and leaves remaining promises unobserved — the tick would skip auto-advance + reconcile and the unhandled-rejection trap would log siblings out of order. `allSettled` resolves only after every promise settles and never throws. The AC pins this with a three-dispatches-one-rejects case.

## Error handling: throw is the default

The only swallow is `Promise.allSettled` on dispatches (required by AC 2). Everywhere else — `fetchSnapshot` rejection, `applyAdvance` rejection, any reconcile runner rejection — propagates out of `tick` and out of `runCycle`. The launcher owns the top-level catch + restart policy. No try/catch was added speculatively; per CLAUDE.md "Don't write a defense for a failure mode that hasn't been observed."

## Capacity threading: caller pre-subtracts for `selectDispatches`, callee subtracts for `decideAutoAdvance`

| Scenario | `capacity` arg to `selectDispatches` | `decideAutoAdvance` internal capacity |
| --- | --- | --- |
| `inFlight=0, max=2` | 2 | 2 |
| `inFlight=1, max=2` | 1 | 1 |
| `inFlight=2, max=2` | 0 | 0 — binding cap |
| `inFlight=3, max=2` (transient) | 0 | 0, no throw |

The asymmetry (caller subtracts on one arm, callee on the other) is intentional: `decideAutoAdvance`'s shape was fixed in #52 to own the formula; `selectDispatches` was fixed earlier to take a raw cap. Mirroring the formula at the caller for the dispatch arm keeps both gates aligned without breaking either pure function's contract.

## Test surface

Eight `it` cases under one `describe`:

1. Happy path — all five steps in order, both arms produce work
2. AC 2 — rejecting dispatch isolated, tick continues
3. AC 3 — drain between ticks stops the loop
4. AC 3 — drain mid-tick still awaits in-flight dispatches (deferred-promise fixture)
5. AC 3 — drain pre-raised → zero work
6. AC 4 — `inFlight === max` → both arms empty, reconcile still runs
7. AC 4 — partial in-flight clamps both arms to the same `capacity`
8. Idle empty board → reconcile still runs

The `oneTick()` helper aborts the drain inside the recorded `sleep` thunk — that's how multi-tick tests collapse to exactly one tick without timing.

What is NOT tested here (covered elsewhere):

- `selectDispatches` / `decideAutoAdvance` semantics — covered in their own files.
- The four runner internals — each has its own `test/loop/run*.test.ts`.
- SIGTERM wiring — the launcher owns it.
- Poll-interval timing — `sleep` is DI'd; the test only asserts it was called.
- `fetchSnapshot` rejection — no observed failure mode yet.

## Patterns established

- **Caller-side capacity math when the callee takes a raw cap.** `selectDispatches` takes `capacity`; the caller computes `max(0, maxConcurrent - inFlightCount)` before passing it in. Future gates may follow either convention; the rule is that the throughput-equation invariant — both arms see the same effective cap — must hold at the call site that touches both.
- **Pre-bound thunks over union-deps.** When a function composes N siblings each with their own narrow deps, take N thunks rather than the union. The launcher is the single binding site.
- **`AbortSignal` checked at boundaries only.** Mid-operation cancellation requires every downstream path to honour the signal; until those paths exist, restrict checks to safe boundaries (tick head, post-tick, pre-sleep).
- **`Promise.allSettled` is the right primitive when sibling isolation is in the AC.** `Promise.all` is wrong when the spec says "one rejection does not abort siblings."
- **Unconditional reconcile.** The maintenance pass runs even on empty boards / pre-raised drain ticks — pinned by tests so a future "optimisation" can't quietly skip it.
