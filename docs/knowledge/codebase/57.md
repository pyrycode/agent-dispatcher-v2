# #57 — `src/loop/runDoneCleanup.ts` per-cycle Done-column label strip

First file under `src/loop/`. Lands a maintenance routine (`runDoneCleanup(deps) → Promise<void>`) that re-asserts the `In Documentation → Done` strip rule against every Done item each dispatch cycle. The routine reads items via an injected port, computes the label delta through `decideLabelDelta`, and calls `removeLabel` on the result. Consumer (not yet built): the dispatcher loop runner that will invoke this alongside the three other per-cycle routines.

## Surface

- `runDoneCleanup(deps)` — async, no return value. Iterates items sequentially.
- `DoneCleanupDeps = { listItems, removeLabel }` — narrow port shape. **Not** `GitHubProjectClient` / `GitHubLabelsClient` — only the two methods the runner calls. Production wiring passes bound methods; tests pass hand-rolled fakes.
- `DoneCleanupItem = { issueNumber, status, labels }` — minimal projection of `ProjectItem`. The full project-client struct is intentionally not imported.

## Why these contracts

### The `decideLabelDelta` call shape is fictitious-but-load-bearing

The runner calls `decideLabelDelta({ column: "In Documentation", labels }, { column: "Done", labels: [] })`. The "before" column is fictitious — the item is *already* in Done — but the framing is "if this ticket were to enter Done now, what would get stripped?". Empty `after.labels` collapses the delta algorithm's `!afterSet.has(l)` predicate to true for every current label; the strip-prefix predicate from the transition row (`strips: ["ready:*", "needs-rework:*"]`) is then the sole filter. This is how the runner satisfies the CLAUDE.md "decideLabelDelta is the only place labels mutate" rule without re-encoding strip prefixes locally. Future strip-set widening (e.g. adding `wip:*` to the row) propagates here automatically.

### `Label` cast on `item.labels` is intentional widening

`ProjectItem.labels` is `readonly string[]` (carries `size:*` / `priority:*` / arbitrary user labels). `decideLabelDelta` parameter is `readonly Label[]`. The cast at the call site is structurally safe — the decision function only inspects labels via `.startsWith(...)` / `.includes(...)`, so non-`Label` strings simply fail the strip-prefix test and pass through. A `validateLabels` filter would be **wrong**: it would mask future strip-prefix additions (any newly-stripped prefix that isn't yet in the `Label` union would be silently dropped before the decision sees it).

### Sequential `for...of`, not `Promise.all`

The Done column is small (terminal items get archived/closed downstream), and `removeLabel` is GET-then-PUT-only-if-present (two round-trips per call). Parallelism would amplify rate-limit pressure without meaningful latency gain. Sequential is the conservative default; switch only if profiling shows it mattering.

### Two idempotency layers, no third

1. `decideLabelDelta` returns `{ remove: [] }` when no current label matches the strip-prefix patterns.
2. `removeLabel` is GET-then-PUT-only-if-present (`src/github/labels.ts`) — removing an absent label is a single GET, no PUT, no throw.

Either layer alone is sufficient; together they cap the cost of a redundant invocation at zero GitHub mutations. No third layer ("skip items already known clean") is needed — the cost is already zero.

### No try/catch

`listItems` and `removeLabel` propagate transport errors verbatim, matching the no-catch posture across `src/github/*`. The (future) loop runner decides whether to abort the cycle, log-and-continue, or trip a breaker. A try/catch in this file would swallow a real GitHub outage.

## Patterns established by this ticket

- **`src/loop/` is for per-cycle I/O orchestrators.** Files here own the read-decide-write cycle around a pure decision function in `src/pipeline/`. They are async, sequential by default, and take an injected dependency object (narrow port, not a full client). This is the template for the three sibling routines still to land (closed sweep, auto-merge, rework routing) and for the eventual loop entrypoint.
- **Narrow DI ports, not full clients.** Inject `{ listItems, removeLabel }`, not `GitHubProjectClient` + `GitHubLabelsClient`. The port shape is the test surface; the production wiring passes bound client methods in one or two lines at the launcher. This keeps test fakes to object literals and forecloses test-bleed from unrelated client methods.
- **"Fictitious before column" idiom for re-asserting a strip rule.** Calling `decideLabelDelta` with `before.column = "In Documentation"` for an item already in Done is the documented way to apply an entry transition's strip rule outside the transition itself. Future maintenance routines that need to re-assert *other* transition strips should reuse this idiom rather than reimplementing strip-prefix logic.
- **Stacked idempotency over pre-flight gating.** Two cheap idempotency layers downstream beat one "is this item dirty?" check upstream. The downstream layers exist anyway; the upstream check adds branching with no payoff.

## Lessons learned

- **Don't filter labels before handing them to `decideLabelDelta`.** The temptation to drop "irrelevant" labels (size/priority/anything-not-in-`Label`) at the call site looks like type hygiene but actually couples the runner to today's strip-prefix list. The decision function's filter is the strip authority; pass labels through unchanged.
- **Empty `after.labels` is the right "strip everything" shape — not a deletion-mode flag.** A first instinct is to add a `mode: "strip"` parameter to `decideLabelDelta`. Resist: the existing semantics already produce the desired behaviour when `after.labels = []`, and adding a mode flag would create a second path through the decision function that future strip-rule changes have to keep in sync.
- **`status` is a string, not an enum.** `ProjectItem.status` carries the column name verbatim from the GitHub Projects API. The runner's `item.status !== "Done"` guard is a string compare — there is no Column union to import. Don't introduce one in this file; if a future ticket needs one, it lives in `src/github/project-client.ts`, not here.

## Out of scope (deferred to the loop ticket)

- **Wiring `runDoneCleanup` into the dispatcher loop.** No `src/loop/run.ts` / `src/dispatch-bin.ts` consumer exists yet. The launcher will bind `client.listItemsInBoardOrder` and a label-client method into `DoneCleanupDeps` in one or two lines.
- **The three sibling routines** — closed sweep, auto-merge, rework routing. Each lands in its own ticket and follows this file's shape.
- **Forward auto-advance `In Documentation → Done`.** This runner only handles drift *after* Done is reached; the transition itself is a separate runner.
