# #68 — `PYRY_PARENT_ITEM_ID` env var on the spawn descriptor

Surfaces the dispatched ticket's GraphQL project-item ID to the spawned agent as the env var `PYRY_PARENT_ITEM_ID`. The consumer is PO's splitting flow (in the agents-repo `po/CLAUDE.md`, not this repo): when PO splits a ticket, the new children call `updateProjectV2ItemPosition` with `afterId: $PYRY_PARENT_ITEM_ID` so the children land immediately after the parent in Backlog instead of leapfrogging higher-priority unrelated tickets to the top of the column. The v1 stopgap (PO runs its own GraphQL `projectItems` lookup) shipped 2026-05-11 and gets ripped out at v2 cutover.

This ticket lands only the dispatcher-side **contract** — the optional state field plus the env-merge — not the dispatch-entry call site that populates it. Populating `parentProjectItemId` from the dispatcher's project-board response is [#78](https://github.com/pyrycode/agent-dispatcher-v2/issues/78)'s job. Until #78 lands, the new field stays `undefined` in production and the new env-merge branch is exercised only by the unit tests.

## Files touched

- `src/dispatch/state.ts` — `DispatchState` gains one optional `readonly parentProjectItemId?: string` field. Comment cites #68 (consumer) and #78 (wiring).
- `src/dispatch/prepareAgentSpawn.ts` — env-merge step appends `PYRY_PARENT_ITEM_ID` to the descriptor's env after `scrubEnv` runs, iff `state.parentProjectItemId !== undefined`. Module header gained one sentence on the merge-order rationale.
- `test/dispatch/prepareAgentSpawn.test.ts` — three new tests: included-when-set, absent-when-unset (via `in` operator, not `=== undefined`), and post-scrub merge doesn't re-introduce denylisted keys.
- `test/claude/spawn.test.ts` — one new by-name pin asserting `SPAWN_ENV_DENYLIST.has("PYRY_PARENT_ITEM_ID") === false`.
- `docs/specs/architecture/68-pyry-parent-item-id-env-var.md` — architect's spec.

No new source modules. `AgentSpawnDescriptor` / `PrepareAgentSpawnDeps` are unchanged. `SPAWN_ENV_DENYLIST` is unchanged.

## Patterns established

- **First `PYRY_*` ticket-context env var to the spawned agent.** Until this ticket, `prepareAgentSpawn` returned `scrubEnv(parentEnv)` verbatim — no dispatcher-internal state crossed into the child's env. `PYRY_PARENT_ITEM_ID` is the first; future ones (PYRY_PARENT_ISSUE_NUMBER, PYRY_RUN_ID, etc.) follow the same shape: a `readonly` optional field on `DispatchState`, an `=== undefined ? scrubbed : { ...scrubbed, KEY: value }` ternary in `prepareAgentSpawn`, and a by-name `SPAWN_ENV_DENYLIST.has("KEY") === false` pin in `test/claude/spawn.test.ts`. Two becomes three becomes a list and at that point you extract a helper — but per CLAUDE.md "no premature abstraction," the first three live as repeated ternaries.
- **Env-merge happens AFTER `scrubEnv`, not before.** The dispatcher-internal `state.parentProjectItemId` is not inherited from `parentEnv` — it's constructed by the dispatch caller from the project-board response. Merging post-scrub means the inner ticket's state always wins regardless of what `parentEnv` happens to contain, and trivially handles the (unlikely) case where the dispatcher process itself was spawned with `PYRY_PARENT_ITEM_ID` set. The alternative (mutate `parentEnv` upstream, then scrub) would entangle scrubber input with caller state and force every future ticket-context var through a second touch.
- **`=== undefined` is the only sentinel that triggers omission, not `!= null` and not truthy-check.** AC bullet 2 ("omits the variable entirely (not empty string) when unset") forced the choice. Empty-string `parentProjectItemId` lands verbatim; we don't invent a "really unset" predicate inside `prepareAgentSpawn`. If a future caller has reason to pass empty-string, that's a caller bug to fix at the call site, not a sentinel to absorb here.
- **By-name denylist pins are documentary, on top of the exact-contents pin.** `test/claude/spawn.test.ts:30-34` already deterministically fails if anyone adds a key to `SPAWN_ENV_DENYLIST` (the `EXPECTED_DENYLIST` array would no longer deep-equal). The new `SPAWN_ENV_DENYLIST.has("PYRY_PARENT_ITEM_ID") === false` test is redundant for *detection* but load-bearing for *intent*: a future contributor reading the test discovers the consumer-side dependency (#68 → PO) and is forced to think before adding the key. When a future `PYRY_*` ticket-context var lands, add a sibling by-name pin in the same `describe`.
- **Absence-check uses the `in` operator, not equality with `undefined`.** `expect("PYRY_PARENT_ITEM_ID" in result.env).toBe(false)` distinguishes "key absent" from "key present with `undefined` value" — both `result.env.X === undefined` is true. The AC explicitly forbids "empty string" emission; the `in` operator is the only way to pin that the *key itself* is absent. Future env-presence tests should mirror this.

## Lessons learned

- **An optional field addition to `DispatchState` is non-breaking by construction, but you still verify.** The architect's spec called out that the four sibling `makeState` test helpers (handleDispatchError, handlePostRun, cleanupAfterDispatch, setupBranchAndWorktree) use `Partial<DispatchState>` and therefore don't need edits. That was correct, but the heuristic to confirm is "does every existing test construct a state that satisfies the *required* fields, with the new field being structurally absent?" — not "is the field optional?" Optional-on-the-type and present-in-every-test-construction are different statements; the former implies the latter only when callers spread an override bag.
- **The architect's "two branches, not three" framing matters.** The ternary deliberately preserves reference identity with `scrubbed` in the unset path (no clone, no extra allocation) and only spreads-and-adds in the set path. An earlier draft would have always built a new object — fine semantically, but it weakens the "scrubbed env is forwarded untouched when no contract requires otherwise" reading. Future ticket-context env merges should follow the same shape: ternary with the `scrubbed` reference-identity branch.

## Out of scope (deferred follow-ups)

- **Populating `parentProjectItemId` at the dispatch entry point.** Belongs to [#78](https://github.com/pyrycode/agent-dispatcher-v2/issues/78) and successors. The dispatcher's project-board response carries the item ID; threading it into the `DispatchState` constructor is that ticket's contract.
- **PO's `po/CLAUDE.md` change to use `afterId: $PYRY_PARENT_ITEM_ID`.** Lives in the `agent-dispatcher-v2-agents` fork (and the three production agents forks), not this repo. The switch from `afterId: null` to `afterId: $PYRY_PARENT_ITEM_ID` happens at v2 cutover; the v1 stopgap covers the gap.
- **Generalizing to a `PYRY_*` env-var registry.** Premature with one variable. When the second and third land, revisit. Until then, repeat the ternary.
