# #9 — `src/claude/stream.ts` pure parser for Claude CLI's `stream-json` output

First file under `src/claude/`. Lands a single pure function (`parseStream`) and three exported types (`StreamParseResult`, `ExitReason`, `ParseStreamOpts`) that turn a buffered `claude -p --output-format stream-json` stdout buffer into the five fields downstream code needs: total cost, sessionId, the last assistant message, the last N assistant messages, and a closed-set exit-reason discriminant.

## Why a pure function (vs. a streaming parser)

This module has no consumers yet. When `src/loop/` lands, it will spawn the CLI, accumulate stdout, and call `parseStream` on the full buffer at process-close time. Pure-function shape keeps the parser trivially testable (string → struct) and frees the I/O layer to manage subprocess lifecycle without a parser callback shape leaking into it. If a future ticket needs incremental parsing (e.g. live dashboards), it can wrap a streaming layer around the same message-shape narrowing — but YAGNI applies today.

Placement under `src/claude/` (not `src/pipeline/`) follows directory semantics: this consumes a Claude-specific I/O format, so it belongs alongside the future I/O-edge code that will own subprocess lifecycle. Purity is incidental, not the routing rule.

## Exit-reason mapping

`mapExitReason` is data-driven over `result.subtype` and `result.terminal_reason`, with one stochastic edge: `/rate.?limit/i` against `result.result` as a final fallback for the rate-limit branch. That fallback is load-bearing — rate-limit routing (back off + retry later) materially differs from generic `error` routing (escalate to human), and a future SDK introducing a new rate-limit subtype must still route correctly even before we add a fixture for it.

The `subtype` enumeration is **best-effort, not exhaustive**. Compile-time exhaustiveness over a `const` union (with a `never`-typed `default`) was considered and rejected: a TS compile error in a deployed dispatcher when the SDK adds a new subtype is worse than a runtime fall-through to `"error"`. The discipline is growing fixtures + rows whenever a new subtype is observed.

`error` is the closed-set catch-all for anything unmapped *and* for streams that died before the result message (subprocess timeout, broken pipe).

## Malformed-line policy

Skipped silently. No throws, no callbacks, no try/catch wrapping the whole loop — the only `try/catch` is around `JSON.parse` for the line, and the catch body is `continue`. This matches v1's `dispatch.ts:284-292` behaviour: when a subprocess kill fires mid-write, the last line is partial JSON; dropping it is the entire error policy. The I/O caller can log raw lines if it cares — that's not the parser's job.

The same skip-on-non-JSON path is what lets the `// SYNTHESIZED FIXTURE` marker lines in `rate_limit.jsonl` / `error.jsonl` ride through without special-casing.

## Fixtures

Four fixtures under `test/fixtures/claude-stream/`, one per exit-reason branch:

- **`success.jsonl`** — real capture: `claude -p --output-format stream-json --verbose --max-turns 2 "Reply with the single word PARSER..."`. 4 lines.
- **`max_turns.jsonl`** — real capture: piped a tool-using prompt with `--max-turns 1 --allowedTools Bash`. The CLI emits `subtype: "error_max_turns"` and `terminal_reason: "max_turns"`. 6 lines, includes one assistant text block before the wall (which pins the "captures text emitted before the wall" assertion).
- **`rate_limit.jsonl`** — synthesized per the spec's rule: verbatim init line from `success.jsonl` + a hand-authored result line with `subtype: "error_rate_limit"` and `terminal_reason: "rate_limit"`, with a leading `// SYNTHESIZED FIXTURE` marker so a future reader can identify it as not-fully-captured. The parser's malformed-line skipping handles the marker.
- **`error.jsonl`** — synthesized the same way: verbatim init line + result line with `subtype: "error_during_execution"` (an unrecognized value), to pin the parser's "anything unmapped → error" branch.

Per the ticket body's "fixtures should be captured verbatim" rule: lines that *are* JSON in the synthesized fixtures match plausible CLI output shapes; the synthesis is by **substitution of the result line** and a non-JSON marker comment, not by editing other JSON content. Every parser bug found in production must become a permanent regression — add a fixture under `test/fixtures/claude-stream/` and a corresponding assertion.

## Test surface

`test/claude/stream.test.ts`, vitest, RED-first. 27 tests across eight `describe` blocks — one per AC bullet plus edge-case groups for malformed input, `lastN` behaviour, and exit-reason fallback signals.

The `excludes tool_use and tool_result blocks` test is the explicit pin for the "tool blocks not in `lastNAssistantMessages`" scope decision. The `routes via /rate.?limit/i in the result text` test pins the load-bearing stochastic edge in `mapExitReason`.

## Out of scope (deferred follow-ups)

- Wiring `parseStream` into `src/loop/` or `src/salvage/`. Those modules don't exist yet; consumer tickets will import from this file.
- A streaming / incremental parser. Current call shape is "buffer the full stream, then parse" — matches v1.
- Field-by-field validation of the `result` message (e.g. `num_turns >= 0`). The parser extracts the five things the AC names; everything else is the caller's problem.
- A Zod / runtime-schema dependency. The narrow `Record<string, unknown>` accessors are sufficient for a 127-line module.
- Capturing fixtures from the IDE's session JSONL files at `~/.claude/projects/<encoded-cwd>/sessions/`. Different shape (queue-operation envelopes, no `result` message); a future ticket gets its own parser if it needs to read those.
- Replacing the synthesized `rate_limit.jsonl` / `error.jsonl` with real captures the next time matching events fire in production. The synthesis policy keeps AC's "minimum four fixtures" satisfied today; replacement is a clean follow-up that drops the marker comment lines.
