# #41 — `src/github/pr.ts` PR-surface I/O (createPr / enableAutoMerge / mergePr)

Fifth file under `src/github/`. Three thin PR-surface I/O ops shared between the loop's `runAutoMerge` and the salvage flow's draft-PR creation. Single GraphQL transport seam from #19; class binds `(repositoryId, owner, repo, transport)` once. The load-bearing piece — the only reason this ticket exists separately from #36 — is `mergePr`'s **conflict-as-typed-value** return shape: a transport-level merge conflict surfaces as `{ merged: false, reason: "conflict" }` rather than a thrown `Error`, so the loop layer can roll project status back from Done → In Code Review without the call site catching strings.

## Exports

- `GitHubPrClient.initialize({ owner, repo }, transport)` — async factory; the only entry point. Resolves the repository node ID up front so `createPr` can mutate against `repositoryId` and the number→nodeId helpers can hit `repository(owner:$o,name:$r){pullRequest(number:N){...}}` without a per-call indirection. Mirrors `GitHubProjectClient.initialize` (#19).
- `client.createPr({ title, body, head, base, draft? }) → PrInfo` — single GraphQL `createPullRequest` mutation. `draft` defaults to `false` via `?? false`; both consumers (salvage `draft: true`, developer flow `draft: false` / omitted) go through the same op.
- `client.enableAutoMerge(prNumber): Promise<void>` — number→nodeId resolution then `enablePullRequestAutoMerge` mutation. Two calls. Errors propagate verbatim; no conflict typing here (GitHub queues auto-merge even when the PR is currently conflicting; conflict is `mergePr`'s concern).
- `client.mergePr(prNumber): Promise<MergeResult>` — number→nodeId then `mergePullRequest`. Returns the discriminated-union `MergeResult`; **does NOT throw** on transport failure.
- `PrInfo` — `{ number, nodeId, url }`.
- `CreatePrInput` — `{ title, body, head, base, draft? }`.
- `MergeResult` — `{ merged: true } | { merged: false, reason: "conflict" | "other", error: Error }`.

`classifyMergeError`, `resolvePrNodeId`, the raw response interfaces, and the GraphQL query strings are file-local. `GraphQLTransport` is re-imported from `project-client.ts` (single source of truth for the DI seam, established by #37).

## Invariants encoded

- **`mergePr` returns conflict as a typed value, NOT a thrown error.** This is the entire reason the ticket exists. v1 lesson 2026-05-09 evening: `runAutoAdvance` moved a ticket to Status=Done as soon as `ready:documentation` landed; auto-merge then attempted `gh pr merge`, which **failed on conflict**; without a typed value the dispatcher swallowed the merge failure and treated the ticket as Done forever, while the PR sat unmerged. The loop now composes this module's `MergeResult` with the project-client's status mutation: on `{ merged: false, reason: "conflict" }` the caller rolls Status back from Done → In Code Review and labels `error:merge-conflict` for human triage.
- **The conflict path is the ONLY place this file deviates from the `src/github/` "errors propagate verbatim" stance.** All other methods (`initialize`, `createPr`, `enableAutoMerge`, the private `resolvePrNodeId`) follow #19/#37 — no try/catch, no fallback retry, no message rewriting. Test #4 in `createPr` (`HTTP 500: server` THROWS) and the asymmetry's structural absence of try/catch elsewhere are the canaries; the `mergePr` typing is the deliberate exception.
- **The `try/catch` wraps the entire `mergePr` body, not just the mutation.** Resolution failures (PR not found by number) also surface as `{ merged: false, reason: "other", error }`. The strict reading of the AC ("`mergePr` returns `{ merged: false, ... }` on failure") matches "all failures are typed"; the loop layer is simpler when one method has one return contract. The substring classifier doesn't misroute a "Pull request not found: ..." message as conflict because that message doesn't include any of the conflict tokens. Test #5 (`mergePr` resolution failure → `reason: "other"`) pins this.
- **Substring classification is lowercase + conservative.** `classifyMergeError` lowercases and matches `"not mergeable"` (canonical GraphQL message for `mergePullRequest` against a conflicting PR), `"merge conflict"`, and bare `"conflict"` (belt-and-suspenders against minor wording variations observed in REST contexts and worth covering in case GraphQL drifts toward parity). Test #4 (case-insensitive — uppercase input still classifies as `conflict`) pins the lowercase normalization. The fragility against GitHub error-message wording drift is intentional: a future drift breaks a test in CI, not in production.
- **Substring-match over a pre-flight `mergeable` query.** A pre-flight `pullRequest(number:N){mergeable}` adds one round-trip on every successful merge — the dispatcher merges every successful ticket, so this is the hot path. The classifier keeps the happy path at one resolve + one mutate (two calls); a pre-flight would make it three.
- **`createPr` body shape pinned by deep-equals tests.** Test #1 deep-equals `t.calls[1]?.variables` to lock `{ repositoryId, title, body, baseRefName, headRefName, draft: false }`. Test #2 separately pins `draft: true` AND `headRefName === input.head` / `baseRefName === input.base` (head/base must NOT swap). Same role-mapping defense as #37's `issueId/blockingIssueId`.
- **`draft` is a required-with-default `Boolean!` GraphQL variable.** The mutation always sends `true` or `false` on the wire — never omits the key. If the variable were optional and the call omitted it, GitHub's GraphQL would silently default to `false` (same end state), but the test mock would have to match a wire shape that omits the key vs sends `false`, which is fragile. Required-with-explicit-default makes the wire shape predictable.
- **No ordering derived from `issueNumber`.** PO-note guard from #19, structurally not applicable here (this module doesn't list anything), but pinned in the spec — `mergePr`/`enableAutoMerge` key on `prNumber` directly, no sort.
- **Per-call, one-shot semantics.** `mergePr` does NOT retry across cycles. The cross-cycle `merge-attempt:N` retry counter (v1 lesson 2026-05-10 evening, `agent-dispatcher@aa588bf`) is the loop layer's concern; this module is one shot, typed result, no internal retry.

## Design choices

- **GraphQL throughout, not REST + GraphQL hybrid.** Three constraints make GraphQL the right single transport: (1) `enablePullRequestAutoMerge` is GraphQL-only — GitHub does not expose a REST endpoint for auto-merge enable; (2) PR node IDs are returned natively from `createPullRequest`; (3) #19's factory pattern fits cleanly. Mixing transports would mean storing both a REST and a GraphQL transport on the client, doubling the DI surface and the test-mock surface for marginal call-site simplicity. The cost is the number→nodeId resolution round-trip in `enableAutoMerge`/`mergePr` (REST keys on number directly); two calls per op is acceptable for the simpler launcher wiring and uniform test posture.
- **Async factory + private constructor** (mirrors #19 exactly). Preflight `repository(owner:$o,name:$r){id}` query resolves the repository node ID once; methods rely on the cached `repositoryId` without `if (!repositoryId) throw "Not initialized"` defensive guards. `owner`/`repo` are stored alongside `repositoryId` because the PR-by-number queries traverse via `repository(owner:$o,name:$r){pullRequest(number:N)...}` — GraphQL has no "PR by number-only" entry point. Storing the trio is one ctor parameter; the alternative (re-passing them at every call) is API noise.
- **Class, not free functions.** Three methods + cached `repositoryId` justify the class shape. `blocked-by.ts` (#37) is a free function because it has no state to bind; this client binds `(repositoryId, owner, repo, transport)` once.
- **Private `resolvePrNodeId` helper.** Only `enableAutoMerge` and `mergePr` need it. Same defensive throw-on-null shape as `initialize`'s "Repository not found." When called from `enableAutoMerge` the throw propagates per the verbatim-errors rule; when called from `mergePr` the surrounding try/catch types it as `reason: "other"`.
- **Imports `GraphQLTransport` from `project-client.ts`** — single source of truth for the DI seam (third in-`src/github/` consumer; per #37 the promotion to `src/github/transport.ts` is deferred until a third sibling appears, and this is now that third sibling — but #37 didn't promote either, so the directory keeps its existing import convention; one more is the cheaper-to-revert default).
- **GraphQL queries are top-level minified single-line `const`s** (matches `project-client.ts:47-50`). Multi-line indented queries push the file past the 200-line hardcap; queries are opaque to the rest of the system.
- **No `enableAutoMerge` conflict typing.** Enabling auto-merge succeeds even when the PR is currently conflicting (GitHub queues the merge until mergeable). The conflict surfaces only at merge-attempt time, which is `mergePr`'s scope.
- **No `mergePr(prNumber, opts?: { nodeId?: string })` overload.** The salvage flow's `createPr → enableAutoMerge` could pass `PrInfo.nodeId` straight through to skip the resolve roundtrip. Out of scope per AC. Additive, non-breaking when an observed hot path needs it.

## Test surface

`test/github/pr.test.ts`, vitest, RED-first per CLAUDE.md. 11 `it` blocks across four `describe` blocks (`initialize`, `createPr`, `enableAutoMerge`, `mergePr`) plus an inline `makeTransport(routes)` helper that mirrors `test/github/blocked-by.test.ts:8-33` and `test/github/project-client.test.ts:8-32`. Per the #37 spec, do NOT extract to a shared `test/github/_helpers/transport.ts`; one more inline copy is the cheaper-to-revert default.

A `makeClient` test factory wraps the common preflight wiring so each test's routing table only declares its own ops; both `REPO_ID_ROUTE` and `PR_ID_ROUTE` are shared `Route` constants at the top of the file.

The load-bearing rows:

- **Test #7 — `mergePr` conflict surfaces typed (no throw).** The entire ticket exists for this canary. Mutation route throws `Error("Pull Request is not mergeable: ...")`; the test does NOT wrap in try/catch — `await client.mergePr(42)` resolves; result deep-equals `{ merged: false, reason: "conflict", error: <Error with "not mergeable"> }`. A future "throw on conflict" simplification fails this immediately.
- **Test #8 — `mergePr` non-conflict transport failure → `reason: "other"`.** The classifier MUST NOT misroute `HTTP 500: server` as conflict.
- **Test #9 — case-insensitive substring match.** Uppercase `"NOT MERGEABLE"` still classifies as `conflict` — pins the lowercase normalization in `classifyMergeError`.
- **Test #10 — resolution failure (PR not found) → `reason: "other"`.** Pins the strict-reading contract: ALL failures (including pre-flight resolution) return typed values; `"Pull request not found: ..."` correctly avoids the conflict tokens.
- **Test #4 — `createPr` transport failure THROWS.** Pins the asymmetry: `mergePr` types failures, `createPr` does not.
- **Tests #2, #3 — `createPr` body-shape and head/base role mapping.** Deep-equals on `t.calls[1]?.variables` lock the wire shape; a future "drop draft when false" simplification or a head/base swap fails the assertions immediately.
