# #36 — `src/github/labels.ts` REST wrappers (addLabel / removeLabel / setLabels)

Fourth file under `src/github/`. The label-mutation primitives the loop applies the deltas decided by `decideLabelDelta` (#5) through. This module makes no decisions; it executes them. `addLabel`'s throw-on-failure is load-bearing for the salvage flow's pre-PR labelling step.

## Exports

- `GitHubLabelsClient.create({ owner, repo }, transport)` — synchronous factory; the only entry point. Constructor is private. Mirrors `GitHubIssuesClient.create` (#35).
- `client.addLabel(number, name)` — `POST /repos/{o}/{r}/issues/{n}/labels` with `{ labels: [name] }`. **Throws on transport failure** — load-bearing.
- `client.removeLabel(number, name)` — GET-then-PUT-only-if-present. Idempotent: removing an absent label issues only the GET, no PUT, no throw.
- `client.setLabels(number, names)` — `PUT /repos/{o}/{r}/issues/{n}/labels` with `{ labels: names }` verbatim. Replace-set semantics; `setLabels(n, [])` strips every label.

All three return `Promise<void>` — callers don't read the post-write label list. Widen at the point of an observed consumer.

## Invariants encoded

- **`addLabel` throws on transport failure.** Load-bearing for the salvage flow (#12): `error:max_turns_salvaged` is applied BEFORE `gh pr create`, and a swallowed-error `addLabel` would produce a labeled-PR-without-label that gets re-dispatched on the next cycle as a normal ready PR. CLAUDE.md "Belt-and-suspenders" — the deterministic transport-level safety net behind the agent's "remember to add the label" prose. Test #2 (`addLabel transport-failure THROWS`) is the canary; pins the `Error` instance + message-substring contract.
- **No conditional read in `addLabel`.** A "skip POST when cached as already present" optimization would open a window where an externally-removed label silently isn't re-added — exactly the salvage failure mode. POST is one call; GitHub dedupes server-side.
- **`removeLabel` is idempotent via GET-then-PUT-only-if-present, NOT via `DELETE` + 404-catch.** The skip-when-absent fast path is the contract the rework-routing flow depends on (don't churn the label set when nothing needs to change). Test #4 (`already-absent — GETs once, NO PUT, no throw`) registers no PUT route, so the routing-table's default-throw catches a future "always PUT for symmetry" simplification.
- **`labels: undefined` leak ruled out by construction.** `setLabels`'s parameter type is `readonly string[]` (not `... | undefined`). `removeLabel`'s PUT body is built unconditionally as `{ labels: next }` where `next` is the `.filter()` result. `addLabel`'s POST body is `{ labels: [name] }` literal. The deep-equals assertions on recorded request bodies are the canaries (#35 PATCH replace-set lesson, generalized to PUT).
- **`setLabels(n, [])` sends `{ labels: [] }`, not `{}` or `{ labels: undefined }`.** Test #6 deep-equals the body — `{}` would be a server-side no-op, `labels: undefined` would 422. Pass-through to the pure pipeline's decision.
- **`mapLabels` defaults to `[]` on shape drift, never throws.** Mirrors `mapIssue`'s field-level type-guard posture in `issues.ts:108-126`. Response-validation belongs at the transport boundary; this module trusts a 2xx body's shape and degrades gracefully if it drifts.
- **All three methods propagate transport errors verbatim — no try/catch anywhere.** The AC only mandates the explicit propagation test for `addLabel`; `removeLabel` / `setLabels` propagation falls out of the no-catch posture (no test, but the structural absence is visible at code review).

## Design choices

- **Static factory + private constructor.** Symmetry with `GitHubIssuesClient` (#35) and `GitHubProjectClient` (#19). Synchronous — endpoints key on `(owner, repo, number)` directly, nothing to resolve up front.
- **Class binds `(owner, repo, transport)` once.** Free functions would force the DI triple at every call site. The salvage flow + rework routing + `decideLabelDelta` consumers all want the context implicit; the class makes it so.
- **Endpoint family consistency: all three target `/issues/{n}/labels`.** Not `/issues/{n}` with the `labels` patch field (that's `updateIssue`'s concern). One path template, three verbs — keeps the test surface narrow and the mental model uniform.
- **No `DELETE /labels/{name}` for `removeLabel`.** GitHub returns 404 when the label is absent, which the transport contract throws on. Idempotency would then require inspecting error shape (`error.status === 404`?) — coupling this module to a transport implementation detail the contract intentionally doesn't expose. GET-then-PUT keeps the transport opaque; idempotency falls out of the filter rather than a typed catch. Two calls is the cost; the dispatcher is single-threaded per ticket so the read/write race is not load-bearing.
- **Asymmetry between `addLabel` and `removeLabel` is deliberate.** `addLabel` failure mode is "salvage PR has no block label" (silent dispatcher loop bug → re-dispatched salvage); `removeLabel` failure mode is "extra GitHub mutation when not needed" (cosmetic). The asymmetry — one always POSTs, the other reads-then-conditionally-PUTs — falls out of the cost ranking, not from a desire for elegance.
- **`RestTransport` union widened by one literal (`"PUT"`).** The PO's technical note explicitly green-lit "widening that union by one literal" as in-scope. Existing callers (`getIssue` / `createIssue` / `updateIssue`) all pass one of the original three literals; widening is additive, no call-site cascade.
- **Methods return `Promise<void>`.** No caller reads the post-write label list. Returning would force a narrow-shape decision and add API surface; widen at the moment a consumer needs it.
- **No `addLabels` batch overload, no `removeLabels` plural, no read helper (`listLabels(n)`).** Per CLAUDE.md "Don't speculate on future consumers" — the salvage flow adds one label at a time; rework routing strips three known names; `decideLabelDelta`'s output goes through `setLabels`. None of the four `decideLabelDelta` mutation sites need a batch-add primitive.

## Test surface

`test/github/labels.test.ts`, vitest, RED-first per CLAUDE.md. Six `it` blocks across three `describe` blocks (`addLabel`, `removeLabel`, `setLabels`) plus an inline `makeTransport(routes)` helper duplicating the shape from `test/github/issues.test.ts:9-37` (third consumer; promotion to `test/github/_helpers/transport.ts` deferred until a fourth — see deferred follow-ups).

The five AC tests in order:

1. `addLabel` happy path — POSTs, body deep-equals `{ labels: [name] }`.
2. `addLabel` transport-failure THROWS — pins the `Error` instance + message-substring; the salvage-flow contract.
3. `removeLabel` happy path — GET then PUT, PUT body deep-equals `{ labels: filtered }` (canary against `labels: undefined` leak).
4. `removeLabel` already-absent — GETs once, no PUT, no throw. Both `t.calls.length === 1` and `t.calls[0]?.method === "GET"` are load-bearing.
5. `setLabels` replaces existing — PUT, body deep-equals input.
6. `setLabels(n, [])` — sends `{ labels: [] }`, NOT `{}`, NOT `{ labels: undefined }`. Regression guard against the lessons.md #35 PATCH replace-set lesson generalized to PUT.

- `addLabels(number, names)` batch primitive. The salvage flow adds one; defer until a multi-add consumer with the same throw-on-failure semantic appears.
- `removeLabels(number, names)` plural. Rework routing strips three known names but composes `setLabels` cleanly via `filter`; defer.
- `listLabels(number)` as a public read helper. The private `fetchCurrentLabels` covers `removeLabel`'s internal need; promote when an external read site appears.
- `DELETE /repos/{o}/{r}/issues/{n}/labels/{name}` primitive. Only useful when a caller wants delete-and-throw-on-absent semantics; not observed.
- Per-issue label cache. Caching belongs at the loop layer; same boundary as #19 / #35.
