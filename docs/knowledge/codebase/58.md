# #58 — `src/loop/runClosedSweep.ts` per-cycle closed-issue → Done reconciliation

Second file under `src/loop/`. Lands a maintenance routine (`runClosedSweep(deps) → Promise<void>`) that moves CLOSED GitHub issues sitting in pre-Done project columns into Done each dispatch cycle. Backstops the v1 lesson *"Closed GitHub issue ≠ removed from project board"* with deterministic per-cycle reconciliation so the dispatcher's selection pass cannot re-dispatch closed work.

Sibling to `runDoneCleanup` (#57); same shape, same conventions.

## Surface

- `runClosedSweep(deps)` — async, no return value. Sequential `for...of`.
- `ClosedSweepDeps = { listItems, setItemStatusToDone }` — narrow port shape. `setItemStatusToDone(itemId)` is intentionally narrower than the underlying `GitHubProjectClient.setItemStatus(itemId, statusName)`: the runner only ever moves to Done, so the production wiring closes over `"Done"` at the launcher and the runner contract carries no magic string.
- `ClosedSweepItem = { id, issueNumber, status, state }` — minimal projection of `ProjectItem`. `id` is the project-item id (`PVTI_*`), not the issue number — passing the issue number to the underlying mutation yields `Could not resolve to a node`.

## Companion changes in `src/github/project-client.ts`

Additive widening of the project-item read + a new mutation primitive:

- **`ProjectItem.state: string`** — GraphQL `Issue.state` enum (`"OPEN"` / `"CLOSED"`, uppercase). Empty-string sentinel on missing/malformed response: neither `"OPEN"` nor `"CLOSED"`, so any predicate gated on the enum skips it. Safer than defaulting to one of the real values.
- **`ITEMS_QUERY`** — `state` added inside the `... on Issue{…}` inline fragment. No new round-trip; the field rides along on every page.
- **`mapItem`** — extracts `state` with the same `typeof === "string"` guard pattern used for `title` / `url`.
- **`setItemStatus(itemId, statusName)`** — new mutation method. Resolves `optionId` via the cached `statusOptionIdsByName` map populated at `initialize` time (no round-trip, no fallback). Unknown `statusName` throws with the name in the message. Takes the project-item id, not the issue number.

## Why these contracts

### Narrower mutation port than the underlying client method

The runner's port is `setItemStatusToDone(itemId)`, not `setItemStatus(itemId, statusName)`. Two consequences:

1. The runner contract carries no `"Done"` string literal — `Column` is not imported. The literal lives at the production wiring site (same precedent as `runDoneCleanup` comparing `item.status !== "Done"` without a `Column` import).
2. The test recorder records one piece of data per call (`{ itemId }`), not two. Recorder shape stays trivial.

### No `issuesClient` despite the AC's wording

The AC mentions an "issue client" port. The architect deviated: the issue's `state` is already in the project-board GraphQL response after the `ProjectItem` widening. Adding a REST `getIssue` per item would be N+1 round-trips for data already on hand. The "DI for fakes" point in the AC is satisfied by `ClosedSweepDeps` alone — the test wires fake `listItems` + fake `setItemStatusToDone` without touching any real client. Same posture as `runDoneCleanup`.

### Predicate stays inline

`state !== "CLOSED" || status === "Done"` is two short-circuits. Per CLAUDE.md *"The 'closed but not in Done' predicate is small; if it grows non-trivial extract a pure function into `src/pipeline/`"* — it doesn't grow here. Inline is correct for this ticket.

### Sequential, no `Promise.all`

Closed-but-not-Done is a recovery case, not a steady state. Zero matches per cycle is the expected mode. Sequential keeps order deterministic for tests and log reading; fan-out is a follow-up if this routine ever becomes hot.

### Idempotency by construction

Status-already-Done items short-circuit before any mutation. Re-invocation issues zero GraphQL writes. One layer (the predicate) is enough — there is no second mutation site to also gate.

### No try/catch

`setItemStatus` errors propagate; a failure on item N aborts the sweep before items N+1…M are processed. Acceptable because the sweep is idempotent and retries next cycle, and failing fast surfaces auth / rate-limit / project-misconfig issues immediately rather than silently dropping work. Same posture as `addBlockedBy` and `runDoneCleanup`.

## Patterns established by this ticket

- **Narrow-port-narrower-than-underlying-method is fine.** When a runner only ever uses one shape of a wider client method, the port should be the narrow shape. Closing over the constant argument at the launcher keeps both the runner contract and the test recorder simpler than passing the wider method through. (`setItemStatusToDone` over `setItemStatus`.)
- **Empty-string sentinel for missing GraphQL enum strings.** When widening `ProjectItem`-style read structs with new enum fields, default missing/malformed values to `""` — neither enum value, so consumers gated on a real value skip it safely. Don't default to `"OPEN"` or any other enum value; that flips the meaning of a malformed response.
- **GraphQL enum field is uppercase.** `Issue.state` returns `"OPEN"` / `"CLOSED"` (uppercase) — predicates compare against the uppercase form. Do not lowercase before comparing.
- **Widen `ProjectItem` per ticket, additively.** The file header already calls this out (*"sibling tickets widen when they need body / blockedBy / etc."*). #58 added `state`; future sweeps add what they need. `codegraph_impact ProjectItem` shows zero external touchpoints — additive widenings are free.
- **Status-mutation goes through the cached `statusOptionIdsByName` map.** `GitHubProjectClient` already caches every Status option id at `initialize`. New mutations that target the Status field should consume this map, not re-fetch. Missing option name → throw with the name; no fallback to a default column.

## Lessons learned

- **Project-item id vs. issue number is a load-bearing distinction.** `setItemStatus` takes the `PVTI_*` project-item id. Passing the issue number throws `Could not resolve to a node`. The narrow port type (`itemId: string`) doesn't enforce the distinction at the type level — a one-line invariant comment above the method documents it. Future mutation primitives on `GitHubProjectClient` should follow the same convention.
- **Don't add a REST `getIssue` per item when the project-board GraphQL already carries the state.** The AC's literal wording suggested an issues-client port; the spec deviated to widen `ProjectItem` instead. The architect-side deviation note (with rationale) belongs in the spec, not as a runtime workaround — the runner's port shape is the load-bearing artifact.
- **Run the closed sweep before the dispatcher's selection pass.** Sequence matters in the (future) loop wiring: if selection runs first, closed-but-not-Done items can still be picked up in the same cycle. Not enforced by this routine — the loop ticket owns the ordering — but the failure mode this sweep is preventing requires the ordering to be right.

## Out of scope (deferred to the loop ticket)

- **Wiring `runClosedSweep` into the dispatcher loop.** No consumer exists yet; the launcher will bind `client.listItemsInBoardOrder` and a closure `(itemId) => client.setItemStatus(itemId, "Done")` into `ClosedSweepDeps` in two lines.
- **The two remaining sibling routines** — auto-merge and rework routing. Each lands in its own ticket and follows this file's shape.
- **Pagination beyond `listItemsInBoardOrder`.** The existing reader already paginates; the sweep inherits whatever the reader provides.
- **Retry / backoff on transport errors.** Owned by the loop layer, not this routine.
- **Fan-out (`Promise.all`) on the mutation step.** Re-evaluate only if profiling shows the serial cost mattering.
