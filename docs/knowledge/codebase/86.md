# #86 — `src/pipeline/classifyAgentResult` (post-run result classifier)

Pure classifier that maps a parsed agent run to a binary post-run branch. The post-spawn orchestrator (a later ticket from the #77 split) calls this to decide whether to advance the ticket or tag it as agent-failed, without parsing stream artifacts inline.

Scope: stream-derived classification only. Label-derived rework detection stays in `decideReworkRouting` (`src/pipeline/routing.ts`); mapping the agent-error subcategories to specific `error:*` labels is the label-delta phase's job (`src/pipeline/decisions.ts` + `transitions.ts`).

## Exports

### `src/pipeline/classifyAgentResult.ts`

- `AgentResultClass` — `"ok" | "agent-error"`. Closed string union, two members.
- `classifyAgentResult(result: StreamParseResult): AgentResultClass` — synchronous, one-expression body: `result.exitReason === "success" ? "ok" : "agent-error"`.

Mapping table:

| `result.exitReason` | result          |
|---------------------|-----------------|
| `"success"`         | `"ok"`          |
| `"max_turns"`       | `"agent-error"` |
| `"rate_limit"`      | `"agent-error"` |
| `"error"`           | `"agent-error"` |

## Why a single conditional, not a `Record<ExitReason, AgentResultClass>`

`routing.ts` uses a `Record<AgentColumn, …>` mapping (`AGENT_TO_COLUMN`) for its 4-key fan-out. The shape doesn't transfer here: this is a 1-vs-N split, not a fan-out. A `Record` would either repeat `"agent-error"` three times (regression-magnet — adding a new `ExitReason` member silently falls through unless every site is touched) or collapse back into a conditional anyway.

The conditional also keeps the conservative default automatic: if a future ticket widens `ExitReason` (e.g. adds `"timeout"`), the new member falls through to `"agent-error"` rather than silently becoming `"ok"` — the safe direction for an unknown new failure mode.

## Why `"agent-error"`, not `"error"`

`"agent-error"` makes the boundary against the dispatcher-side error class (`error:dispatch`, owned by `#77`'s `handleDispatchError`) explicit at the type level. The classifier returns the *agent* class; dispatch-side failures are a separate axis. Plain `"error"` would collide semantically with that other axis.

## Why the discriminant doesn't carry the underlying `ExitReason`

The orchestrator still has the `StreamParseResult` in scope and reads `result.exitReason` directly when it needs the finer-grained reason (e.g. choosing between `error:max-turns` and `error:rate-limit` in the label-delta phase). Embedding the payload in the discriminant — `{ kind: "agent-error", reason: ExitReason }` — would force every caller to destructure it whether they cared or not. Premature shape; narrow union ships now, widen on first observed need per CLAUDE.md "Don't write a defense for a failure mode that hasn't been observed."

## Patterns established

- **Binary discriminants over closed input unions stay binary until a second branch is observed.** This function could have shipped as `"ok" | "max-turns" | "rate-limit" | "error"` — the input union has four members, the mapping is total. It didn't, because no caller today branches on the finer reason; the post-spawn orchestrator reads `result.exitReason` directly when it needs that. Pattern: pick the *narrowest* discriminant that the immediate caller needs, not the widest that the input supports. Widen on the first observed second-branch caller, not speculatively.
- **`1-vs-N` mappings read better as a conditional than a `Record`.** `routing.ts:AGENT_TO_COLUMN` is the existing prior art for the fan-out shape; this ticket is the prior art for the binary-split shape. Future pipeline functions that classify a closed union should pick by counting distinct output values: 1-vs-N → conditional, N-way fan-out → `Record`.
- **Pure pipeline functions document their non-scope in the module header.** The 12-line header on `classifyAgentResult.ts` names what's *not* here (rework detection in `routing.ts`, label mapping in `decisions.ts`/`transitions.ts`) and points at the canonical owner of each. This matters when a future ticket comes back asking "where does X go?" — the header tells the reader where to look instead of expanding this file. Same shape `prepareAgentSpawn.ts` uses (see [#82](82.md)'s "Header comments earn their keep" note).
- **Test the structural invariant with `it.each` over the closed union, not a single spot-check.** The AC asked for "at least one" of the error reasons; the test covers all three via `it.each`. The two extra lines are cheap insurance against the silent-regression case where someone refactors the conditional into a positive-list and only the spot-checked branch stays green. Generalisable to any classifier over a closed string union: every member gets a row.
- **Don't assert exhaustiveness with a re-exported union introspection.** TypeScript already enforces it at the call site via the string-literal type. A test row per member IS the structural invariant — widening `ExitReason` leaves the new member uncovered, which is the right RED signal for the follow-up ticket.
