# #81 — `src/dispatch/` pre-spawn phase 1 + `DispatchState`

First module under `src/dispatch/`. Lands two things together because they're the same contract: the shared `DispatchState` type that every per-ticket dispatch phase will read, and the first phase that consumes it (`setupBranchAndWorktree`). The function is a thin I/O *orchestrator* — it sequences a GitHub lookup, runs the pure create-vs-reuse predicate, and materialises the worktree. All I/O comes through injected deps; no `gh` or `git` shell-out lives in this file.

## Exports

### `src/dispatch/state.ts`

- `DispatchState` — `{ readonly agent: Agent; readonly issueNumber: number }`. Reuses the canonical `Agent` union from `src/pipeline/selection.ts` (imported, not redeclared). Deliberately minimal: fields are added by the phase ticket that first reads them. Don't add `labels`, `worktreePath`, `repoRoot`, etc. pre-emptively.

### `src/dispatch/setupBranchAndWorktree.ts`

- `SetupBranchAndWorktreeDeps` — `{ lookupExistingPrHeadRef: (issueNumber) => Promise<string | null>; createWorktree: (branch) => Promise<string> }`. Both deps are launcher-bound surfaces; this module never invokes the underlying primitives directly.
- `SetupBranchAndWorktreeResult` — `{ branch, worktreePath, kind: "create" | "reuse" }`.
- `setupBranchAndWorktree(state, deps): Promise<SetupBranchAndWorktreeResult>` — awaits `lookupExistingPrHeadRef(state.issueNumber)`, feeds the result into `decideBranchSetup` (with `labels: []`), awaits `createWorktree(decision.branch)`, returns the assembled result. No try/catch.

## Why `DispatchState` lives in its own file

It is the cross-phase contract — every future phase under `src/dispatch/` reads it, and most will extend it. Putting it in a sibling phase file would make every other phase import a `setupBranchAndWorktree` symbol just to get the type. One concern per file (CLAUDE.md hardcap): the type is one decision, the phase function is another.

## Why this module lives outside `src/pipeline/`

`src/pipeline/` is reserved for pure functions (no `await`, no I/O — see CLAUDE.md § "Pure functions in `src/pipeline/`, I/O at the edges"). `setupBranchAndWorktree` is `async` and orchestrates two I/O calls; even though both are injected, the function itself awaits them. The create-vs-reuse *decision* stays pure — delegated to `decideBranchSetup` in `src/pipeline/branch-setup.ts:32` — so the I/O orchestrator never re-derives the rule inline.

## Import contract is the AC

The function body imports only `../pipeline/branch-setup.ts` (pure predicate) and `./state.ts` (sibling type). **Anything under `src/github/` or `src/worktree/` is forbidden in the body.** That's how production I/O would leak in; the launcher does the binding instead, so this file body knows nothing about GitHub or git. The test file enforces the same shape — it imports only the two `src/dispatch/` files and `vitest`. A future refactor that leaks `gh`/git would have to grow such an import to stub it; the absence is the canary.

## Why `labels: []` is passed to the predicate

`decideBranchSetup` accepts `labels` on its input for shape-symmetry with `shouldAutoCommit` but does **not read it** (see `src/pipeline/branch-setup.ts:11-14`). PR-existence is the deterministic disambiguator. Passing `[]` from this orchestrator satisfies the predicate's type without inflating `DispatchState` with a field nothing reads yet. When a later phase needs `labels`, that phase's ticket adds the field to `DispatchState`.

## No try/catch — load-bearing

Same posture as [#71](71.md) and `src/worktree/create.ts`: errors propagate verbatim. If `lookupExistingPrHeadRef` throws, `createWorktree` is never called — the throw IS the gate. If `createWorktree` throws after the lookup succeeded, the orchestrator sees the throw with no partial result. Collision recovery is the caller's concern per the invariant pinned in `src/worktree/create.ts:8-13`. Wrapping in try/catch would defeat the deterministic-safety-net posture the dispatch sequence depends on.

Tests 4 and 5 pin both throw paths; a future refactor that swallows either throw would break the call-count assertions.

## Patterns established

- **Cross-phase contract types get their own file in the package they belong to.** `DispatchState` in `src/dispatch/state.ts`, not co-located with the first phase that reads it. Every subsequent phase under `src/dispatch/` will read this type; sourcing it from the first phase file would make `state.ts` a phase file with an awkward second role. One decision per file (CLAUDE.md hardcap).
- **Extend `DispatchState` only when a phase reads the field.** Resist pre-emptive `labels`, `worktreePath`, `repoRoot`, etc. The ticket that first reads a field is the ticket that adds it. Matches the same "no speculative widening" posture as #41 (`enableAutoMerge` returning `void`) and #71 (`openSalvageDraftPr` returning bare `number`).
- **Pre-bound dep surfaces narrow the primitive's signature.** `createWorktree` the primitive (`src/worktree/create.ts:27`) takes `(branch, repoRoot, worktreeDir, spawn)`. The dep contract here is `(branch) => Promise<string>` — launcher binds the other three once, and this orchestrator passes only the per-call data. Same shape applies to all I/O primitives wired into dispatch phases: bind the static config at the launcher, expose only the per-call edge to the orchestrator.
- **Define new dep seams at the contract level; defer production wiring.** `lookupExistingPrHeadRef` does not exist in `src/github/pr.ts` yet — this ticket defines only the dep *shape*. Adding the production helper is a follow-up ticket. Lets the orchestrator land with full unit-test coverage while postponing the GitHub-side decision (where to put it, what return type to choose for richer PR data) to its own ticket.
- **Forbidden-import contract is enforced by the test file's import list.** The test imports only `vitest` and the two `src/dispatch/` files. If a future refactor pulls `gh` / git into the module body, the test would need to import-and-stub from `src/github/` or `src/worktree/`. The absence of those imports is the structural canary for AC bullet 3 — checked by reading, not by tooling.
- **`(state, deps)` argument order.** Matches the broader DI convention used by [#71](71.md) `(deps, input)` but with `state` first because dispatch state is the per-call object every phase consumes; deps are the wiring bound once by the orchestrator. Phase functions across `src/dispatch/` should follow this same order so the orchestrator's call sites read uniformly.
- **Order-pin test via shared `events: string[]`.** Same pattern as #71: both fakes push their name into a shared array, the test asserts on the exact sequence. Cheaper than spying on timestamps; catches a future `Promise.all` refactor that would interleave the two I/O calls. The two-call sequence here is load-bearing (the second call's branch is derived from the first call's result), so the test pins it.

## Out of scope (deferred follow-ups)

- Wiring `lookupExistingPrHeadRef` to a real GitHub query. `src/github/pr.ts` exposes only `createPr` / `enableAutoMerge` / `mergePr` today; the production helper (likely `findPrByIssueNumber` on `GitHubPrClient` or a sibling) is a follow-up ticket.
- Calling `setupBranchAndWorktree` from a real orchestrator. The orchestrator comes after all per-phase units land.
- Sibling pre-spawn phase `prepareAgentSpawn` — split as #82.
- Post-spawn phases (claude spawn, label mutation, cleanup) — separate tickets.
- Adding `labels`, `worktreeDir`, `repoRoot`, or anything else to `DispatchState`.
- Cancellation / `AbortSignal` plumbing — the future orchestrator handles cross-phase cancellation; individual phases stay signal-free.
