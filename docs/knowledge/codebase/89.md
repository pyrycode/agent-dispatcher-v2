# #89 — `src/dispatch/cleanupAfterDispatch` (exit-path callee releases `wip:<agent>`)

Dedicated cleanup function for the dispatcher's per-ticket flow. Runs on the exit path of every dispatched ticket — happy OR error — after `handlePostRun` (#87) or `handleDispatchError` (#88) has settled, and removes the transient `wip:<agent>` label that pre-dispatch armed to prevent double-dispatch. Without this release the next loop iteration would still see the ticket as "in-flight", `selectDispatches.cap` would short-circuit, and the dispatcher would stall.

Split from #77. Third callee in the dispatcher per-ticket trilogy alongside [#87](87.md) and [#88](88.md); the orchestrator that wires all three into a try/catch/finally is a follow-up.

## Exports

### `src/dispatch/cleanupAfterDispatch.ts`

- `CleanupAfterDispatchDeps` — `{ labels: Pick<GitHubLabelsClient, "removeLabel"> }`. Only `removeLabel` is needed; no `addLabel`, no logger, no project-board client.
- `cleanupAfterDispatch(state: DispatchState, deps: CleanupAfterDispatchDeps): Promise<void>` — one-expression body: build `` `wip:${state.agent}` `` and `await deps.labels.removeLabel(state.issueNumber, …)`.

`DispatchState` is consumed unmodified — only `state.agent` and `state.issueNumber` are read. No status I/O (column doesn't change here either).

## Why no `satisfies Label`

The sibling `handlePostRun` (#87) writes `` `ready:${state.agent}` satisfies Label `` because `ready:*` IS a member of the `Label` union — `satisfies` is the compile-time trip-wire that adding a new `Agent` member without its `ready:*` becomes a type error at the call site. `wip:*` is **not** in the `Label` union (`src/pipeline/transitions.ts:42-51`); that's the whole point of the carve-out. A `satisfies Label` here would refuse to compile. The plain template literal is the correct shape — the `Agent` union narrows the right side, the GitHub label name on the left is documentation.

## Why the carve-out flavour is "flavour 1"

[#87](87.md) named two flavours of carve-out from the "all label mutations funnel through `decideLabelDelta`" rule. This ticket sits firmly in **flavour 1** (dispatcher state, not in the `Label` union at all), alongside:

- `src/dispatch/handleDispatchError.ts` — adds `error:dispatch`.
- `src/salvage/draft-pr.ts` — adds `error:max_turns_salvaged`.

All three call label I/O directly via injected `Pick<GitHubLabelsClient, …>` deps, all three module headers cite `src/pipeline/transitions.ts:38-41` as the source-of-truth comment. This is the first cleanup-side flavour-1 site — the prior two are add-side. Releasing `wip:*` is the symmetric counterpart to arming it (which lands in a separate split from #77).

## Why errors propagate (same contract as `handlePostRun`)

Two siblings, two contracts; this one matches `handlePostRun`'s **propagate** side, not `handleDispatchError`'s swallow side:

| Outcome | Behaviour | Why |
|---|---|---|
| `removeLabel` resolves | resolves void | `wip:<agent>` is cleared; next selection cycle sees a clean slate |
| `removeLabel` throws (HTTP 5xx, network drop) | rejects with the same error | orchestrator's outer `finally`-and-log owns observability; swallowing here would hide cleanup failures and silently strand the issue with `wip:<agent>` stuck on |

The label-already-absent case is **not** a thrown error — `removeLabel` at `src/github/labels.ts:54` is GET-then-PUT-only-if-present, so it resolves cleanly without issuing a PUT. The wrapper inherits that contract without adding its own existence check; doing so would duplicate the underlying I/O. AC bullet 2's idempotency is satisfied by transitive inheritance, pinned by test 2.

## Why no try/catch around `removeLabel`

Mirror `handlePostRun`'s leaner shape, not `handleDispatchError`'s try/catch-around-`addLabel`. The catch-path swallow in `handleDispatchError` exists because that function's job is to keep the loop running after a primary failure — its `addLabel` is best-effort metadata. This function's `removeLabel` is the contractual cleanup itself, not a metadata afterthought; a silent failure here is the exact bug we'd want surfaced to the orchestrator's `finally`-log.

## Why no worktree teardown

Explicitly out of scope per the issue body. The pre-spawn worktree primitive (`createWorktree`, `src/worktree/create.ts:27`) does not yet have a paired teardown surface. When the launcher decides worktrees should be reaped per-dispatch, a sibling `teardownWorktree` lands and the orchestrator's `finally` calls both — this module stays single-purpose.

## Patterns established

- **The dispatcher per-ticket trilogy is `handlePostRun` / `handleDispatchError` / `cleanupAfterDispatch`, three callees with one shared shape.** All three take `(state: DispatchState, deps)`, all three use a `Pick<GitHubLabelsClient, …>` projection for label I/O, all three cite `src/pipeline/transitions.ts:37-41` in their header. Differences are scoped: `handlePostRun` and `handleDispatchError` are mutually exclusive (happy-path vs catch-path); `cleanupAfterDispatch` runs after either, regardless. Future dispatcher-side per-ticket callees that don't fit this trio (e.g. a future `handleSalvageError`) belong as a fourth file with the same shape — not as a branch inside an existing one.
- **The carve-out flavour distinction now has a release-side example.** Prior flavour-1 sites (`handleDispatchError`, `salvage/draft-pr`) are add-side: they apply `error:*`. This ticket is the first release-side flavour-1 site: it removes `wip:*`. Pattern: arming-and-releasing a flavour-1 (non-`Label`-union) label both go through direct injected I/O; only `Label`-union transitions go through `decideLabelDelta`. When adding a future arm-or-release pair for a flavour-1 label, both halves stay outside `decideLabelDelta` and both module headers cite the same `transitions.ts:38-41` block.
- **Pick the propagate-vs-swallow contract per *callee's role*, not per *exit path*.** `cleanupAfterDispatch` runs on the same exit path as `handleDispatchError` (after a failure) AND on the same exit path as `handlePostRun` (after a success), so "exit path" doesn't determine the contract. The callee's role does: best-effort metadata ⇒ swallow (`handleDispatchError`); contractual mutation ⇒ propagate (`handlePostRun`, this ticket). When adding a new exit-path callee, ask which side of that axis it's on before reaching for a try/catch — and state it in the header.
- **Idempotency by transitive inheritance is a valid AC strategy when the underlying I/O already provides it.** AC bullet 2 ("idempotent: no-op when label is absent") is satisfied without a single line of wrapper code — `removeLabel`'s GET-then-PUT-only-if-present makes the wrapper idempotent by virtue of forwarding the call. Pattern: when a wrapper's required property is structurally guaranteed by its callee, cite the callee's contract (file:line) in the header and pin the property with a behavioural test rather than adding wrapper logic. Don't duplicate the safeguard.
- **Test scaffolding (`fakeLabels`, `makeState`) is now copied across three sibling test files.** `test/dispatch/handleDispatchError.test.ts`, `test/dispatch/handlePostRun.test.ts`, and now `test/dispatch/cleanupAfterDispatch.test.ts` each contain a near-identical `fakeLabels({ onAdd | onRemove })` factory and `makeState(overrides?)` defaults. This is deliberate per [#87](87.md)'s pattern — "copy the helpers literally; divergence in fakes between siblings makes drift in the production contracts harder to spot". If a fourth dispatch-phase test file lands, copy these helpers verbatim again. The shared shape is the load-bearing observation; do not extract to `test/dispatch/helpers.ts`.

## Lessons learned

- **The "narrowest shape this phase actually reads" heuristic prunes a `satisfies` annotation here.** Inheriting #87's `satisfies Label` line by reflex would have broken compilation because `wip:*` is not in the `Label` union. The fix is to read the union before borrowing the sibling's idiom — `satisfies` is conditional on `Label` membership, not a universal lint. Future label-add or label-remove sites should check `transitions.ts:42-51` first; if the literal is in-union add the `satisfies`, if it's a carve-out drop it.
- **Three sibling callees mean three sibling test files, and the `Agent`-loop test is non-optional for the carve-out cases.** Both flavour-1 carve-outs (this ticket, and `handleDispatchError` for its label literal) lack a `satisfies Label` to catch a regression at compile time. The `for (const agent of agents) … expect("wip:${agent}")` loop is the *runtime* substitute that pins every `Agent` union member. When adding a fifth `Agent` member, this loop and the matching one in `handlePostRun.test.ts:33-49` must both be updated — there's no compile error to remind you.
