# #88 — `src/dispatch/handleDispatchError` (catch-path callee tags `error:dispatch`)

Dedicated error-path function for the dispatcher's per-ticket `try { … } catch { handleDispatchError(err, state, deps) }`. Tags the issue with `error:dispatch`, logs the original error via an injected logger, and never rethrows — a successful return tells the orchestrator "logged, move on; the loop continues with the next ticket".

Split from #77. The orchestrator that wraps each per-ticket dispatch in the try/catch and consumes this callee is a follow-up; this ticket lands the callee alone so it can ship with its own tests first.

## Exports

### `src/dispatch/handleDispatchError.ts`

- `DISPATCH_ERROR_LABEL = "error:dispatch"` — the label literal.
- `DispatchErrorLogger` — `{ error(err: unknown, context: { issueNumber: number; agent: string; phase: "dispatch" }): void }`. Minimal sink, structured context payload.
- `HandleDispatchErrorDeps` — `{ labels: Pick<GitHubLabelsClient, "addLabel">; logger: DispatchErrorLogger }`. I/O injected; the function body imports only types from `src/github/`.
- `handleDispatchError(error, state, deps): Promise<void>` — logs the original error, then attempts `addLabel`; if `addLabel` throws, the secondary error is logged too and swallowed.

Body shape:

1. `deps.logger.error(error, ctx)` — unconditional, first.
2. `try { await deps.labels.addLabel(state.issueNumber, "error:dispatch") } catch (e) { deps.logger.error(e, ctx) }`.

The function holds no state across calls; safe to invoke once per failed per-ticket dispatch attempt.

## Why `error:*` bypasses `decideLabelDelta`

The CLAUDE.md rule says all label mutations funnel through `decideLabelDelta`. `error:*` is the documented carve-out:

- `src/pipeline/transitions.ts:37-41` — the comment above the `Label` union pins it: `error:*` is dispatcher run-state metadata, not a transition trigger, so it's excluded from the union.
- `src/pipeline/routing.ts:29` — `STRIP_PREFIXES = ["ready:", "wip:", "error:"]`. Rework strips `error:*` automatically, so a dispatch-error label naturally clears on the next agent run; no explicit cleanup belongs in this phase.

That carve-out is why this function legitimately calls `addLabel` directly via injected deps. Prior art: `src/salvage/draft-pr.ts` applies `error:max_turns_salvaged` the same way.

## Why log-before-label, not label-before-log

The original error is the load-bearing observability — it must be captured whether or not GitHub is reachable. If the label-add succeeded but the logger came second and threw, we'd have an `error:dispatch` label on the issue with no log trail (worse than the inverse). Test 3 pins the ordering against future reorderings via a shared `events: string[]` that both fakes append to.

## Why try/catch around `addLabel`, not `.catch()`

Symmetry with `src/salvage/draft-pr.ts`'s inverse contract: salvage's `addLabel` throw is *the* safety net — it must propagate so a label-less salvage PR never gets opened. This catch-path's contract is the mirror: the throw must be swallowed-and-logged so the loop continues. The `try { … } catch { … }` makes the inversion visible at the call site; `.catch()` would obscure it and add an arrow allocation per call.

## What this function deliberately does NOT do

- Does not consult `decideLabelDelta` or any transition-table helper (see carve-out above).
- Does not remove other labels. A failed run may legitimately carry `wip:<agent>` or `ready:<agent>`; the next transition's `decideReworkRouting` cleans them up alongside `error:*`.
- Does not touch the worktree. Worktree teardown is a separate dispatcher-side concern.
- Does not mark the issue blocked or comment on it. The label alone is the marker; comment-on-error can be added later if observability demands it (not observed yet).
- Does not wrap the logger call in try/catch. A synchronous in-process logger that throws is an unrecoverable launcher-side bug, not a runtime failure mode this catch path is designed for — CLAUDE.md "Don't write a defense for a failure mode that hasn't been observed".

## Patterns established

- **The `error:*` carve-out from `decideLabelDelta` is a *named*, *documented* exemption — not a loophole.** Two production sites now legitimately call `addLabel` directly: `src/salvage/draft-pr.ts` (`error:max_turns_salvaged`) and `src/dispatch/handleDispatchError.ts` (`error:dispatch`). Both module headers reference `src/pipeline/transitions.ts:37-41` and `src/pipeline/routing.ts:29` as the source-of-truth pair. Future dispatcher-side `error:*` labels follow the same shape: name the carve-out in the header, point at both source-of-truth lines, take label I/O via `Pick<GitHubLabelsClient, "addLabel">`. If you're adding a new `error:*` site and the header doesn't cite the carve-out, you're skipping the rule.
- **Catch-path callees have an inverted contract from happy-path callees and the header must call it out.** Salvage's `addLabel` throw is the safety net (propagate); this function's `addLabel` throw is one more thing to swallow (the loop must continue). Same I/O, opposite contract. Module headers must state which side they're on; tests pin the chosen side with `.resolves` (this ticket) or `.rejects` (salvage). Both sides exist in the codebase now — read the header before assuming.
- **Logger injection over `console.*` for production sinks, even for one-call functions.** The dep-injected `DispatchErrorLogger` interface (one method, structured context) keeps the function unit-testable without spying on `console`. The orchestrator that lands later will bind a concrete implementation; tests pass a `fakeLogger` that captures calls into an array. Pattern transfers to any future error-path callee — same shape, different `phase` literal.
- **`phase: "dispatch"` as a literal in the context payload narrows the type and self-describes the call site.** Future error-path callees (e.g. a `handleSalvageError` if one ever lands) would pass `phase: "salvage"`. The logger can disambiguate by reading the literal instead of parsing the label name; the discriminated literal is cheaper than a runtime string match.
- **`makeState` factory in the test file keeps the noise out of each `it`.** `DispatchState` carries `worktreePath` and `args` that this function doesn't touch but TypeScript requires; the factory defaults them once. Pattern: when a test file consumes a wider shape than the unit under test reads, build a defaults factory at the top and `Partial<>`-spread per test. Same pattern as `makeInput` in `test/salvage/draft-pr.test.ts`.
- **Test the load-bearing ordering directly with a shared `events: string[]`.** When two side effects have a contractually-pinned order ("log before label"), assert it with an events array both fakes push into — not by inspecting timestamps or call counts on isolated mocks. The single `expect(events).toEqual(["log", "label"])` is the regression trap for anyone who later "tidies" the body into label-first.

## Lessons learned

- **Type-only `import type` from `src/github/` satisfies the "imports nothing from `src/github/`" AC.** TypeScript erases `import type` at compile time, so the JS the function body emits really does have zero `src/github/` reach. Future ACs that say "imports nothing from X" can be satisfied by `import type { … } from "X"` as long as the value-level surface is `Pick<…>`'d into the deps interface — no runtime `import { … }` from X is needed.
- **`await expect(promise).resolves.toBeUndefined()` is the right "does NOT rethrow" assertion.** Stronger than wrapping the call in its own try/catch and asserting no error was caught — `.resolves` is the structural rethrow check; the `toBeUndefined()` half pins the return type. The salvage test's inverse `.rejects.toThrow(...)` is the mirror assertion for the rethrow contract.
