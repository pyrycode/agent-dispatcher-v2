# #82 — `src/dispatch/prepareAgentSpawn` (pre-spawn phase 2)

Second per-ticket phase under `src/dispatch/`. Assembles the `{ args, env, cwd }` descriptor that `spawnClaude` will consume — but does **not** invoke `spawnClaude`. Separating the descriptor from the spawn lets unit tests pin argv shape and env-denylist propagation without touching `child_process`, PATH, or the real env.

Also extends the shared `DispatchState` (added in [#81](81.md)) with the two fields this phase reads: `worktreePath` (→ `cwd`) and `args` (→ `args`).

## Exports

### `src/dispatch/prepareAgentSpawn.ts`

- `PrepareAgentSpawnDeps` — `{ readonly scrubEnv: (env) => NodeJS.ProcessEnv; readonly parentEnv: NodeJS.ProcessEnv }`. The scrubber is launcher-bound to `scrubSpawnEnv` (`src/claude/spawn.ts:51`) in production; `parentEnv` is the *captured snapshot* of `process.env`, passed in as data — the module body never reaches for `process.env`.
- `AgentSpawnDescriptor` — `{ readonly args: readonly string[]; readonly env: NodeJS.ProcessEnv; readonly cwd: string }`.
- `prepareAgentSpawn(state, deps): AgentSpawnDescriptor` — synchronous (no `await`). Returns `{ args: state.args, env: deps.scrubEnv(deps.parentEnv), cwd: state.worktreePath }`. That's the whole body.

### `src/dispatch/state.ts` (extension)

Added two fields to `DispatchState`:

- `worktreePath: string` — populated by the prior pre-spawn phase ([#81](81.md)'s `setupBranchAndWorktree` returns it); consumed here as `cwd`.
- `args: readonly string[]` — caller-supplied tail args for `claude`. `spawnClaude` itself prepends `-p --output-format stream-json` (`src/claude/spawn.ts:60-72`), so this array does NOT include those flags. A future prompt-assembly phase will populate it.

The existing `agent` / `issueNumber` fields are untouched. Field order keeps existing fields first, new fields appended.

## Why the body imports nothing from `src/claude/`

This is AC bullet 2, structurally enforced by the module's import block. The only allowed import is `./state.ts` (sibling type). The launcher (a future orchestrator) imports `scrubSpawnEnv` from `src/claude/spawn.ts` and binds it into `deps.scrubEnv` at startup; the module body never names the `src/claude/` namespace.

If a future refactor leaks `from "../claude/..."` into this file, the architectural contract is broken regardless of test green. The test file is allowed to import `scrubSpawnEnv` and `SPAWN_ENV_DENYLIST` for the "reuses the real scrubber" assertion — the no-`src/claude/` rule is a *module body* rule, not a test rule.

## Why this module lives outside `src/pipeline/`

Same posture as [#81](81.md). `src/pipeline/` is reserved for pure functions; even though `prepareAgentSpawn` is itself synchronous and has no I/O in its body, it orchestrates an *injected* env-scrub surface and is part of the dispatch-side sequence rather than the pipeline-side decision layer. `src/dispatch/` is where launcher-bound DI'd phases live.

## Why `parentEnv` is a dep, not `process.env`

The function never reads `process.env` directly. The launcher captures `process.env` once and passes the snapshot in via `deps.parentEnv`. Two consequences:

1. The module is pure w.r.t. the ambient process — the test suite controls the input verbatim, no `vi.stubGlobal` / monkey-patching.
2. The snapshot's identity is testable: the scrubber-was-invoked assertion uses `calls.scrubEnv[0] === deps.parentEnv` (reference identity), which would silently break if some future refactor decided to clone the env first.

## Why `args` lives in `DispatchState`, not in `deps`

Three positionals are off the table (the ticket fixes the signature as `(state, deps)`). `deps` is launcher-bound — wired once at startup — but `args` is per-dispatch (each ticket has its own prompt). State is the only home that matches the lifecycle.

The prompt-assembly phase that populates `args` is a separate sibling of #76, still unticketed. Until that phase lands, orchestrators must supply `args` explicitly (typically the assembled prompt as a single positional).

## No `await`, no `try`/`catch`

The body is a single `return`. The injected `scrubEnv` is documented as total (production `scrubSpawnEnv` never throws); if a test fake chooses to throw, the throw propagates verbatim. Same posture as [#81](81.md) and the rest of the dispatch sequence — errors are the gate, not something to swallow.

## Patterns established

- **Extending a shared cross-phase type happens in the phase ticket that first reads the field.** [#81](81.md) established `DispatchState` deliberately minimal — `{ agent, issueNumber }`. This ticket reads two new fields, so this ticket adds them. The discipline avoids speculative widening: every field in `DispatchState` has at least one reader at the moment it lands.
- **Descriptor / invocation split.** The pattern: one phase assembles a typed descriptor (data); a separate sibling consumes it to perform I/O. Here, `prepareAgentSpawn` returns `AgentSpawnDescriptor` and `spawnClaude` (in `src/claude/spawn.ts`) consumes it. The split is what lets the descriptor-assembly phase be unit-tested without `child_process`. Reusable shape for any future "build args for an external process" phase.
- **Pre-bound dep surfaces narrow the primitive's signature** (extends the same pattern from [#81](81.md)). Production `scrubSpawnEnv` is `(env) => NodeJS.ProcessEnv`; the dep contract here matches exactly because there's nothing to bind. Where the underlying primitive has static config (as with `createWorktree` in #81), the dep contract narrows away the static params. Either way, the orchestrator passes only per-call data.
- **Inject the ambient process as data.** `parentEnv` is a dep, not a `process.env` reach. The function stays pure w.r.t. its environment; tests pin reference identity. Apply this anywhere a phase would otherwise read process-global state (`process.env`, `process.cwd()`, `Date.now()`, etc.).
- **Module-body import rule is enforced by reading the import block, not by tooling.** Same canary shape as [#81](81.md): the test file's imports document what the *module body* may import. Test imports may be looser than module-body imports — that asymmetry is intentional and documented in the module header.
- **`spawnClaude` owns the `-p --output-format stream-json` prefix.** Descriptor-assembly phases pass *only the tail*. A future phase that builds args should pin this via a test that includes a multi-element `args` and asserts no prepended flags appear in the descriptor — same shape as test case 1 here.
- **Header comments earn their keep when they encode an architectural rule.** The 16-line header on `prepareAgentSpawn.ts` is unusual for this codebase (CLAUDE.md § "Default to writing no comments"). It stays because each paragraph encodes a load-bearing rule: the no-`src/claude/`-import contract, the descriptor-vs-spawn split, the launcher-binding of `scrubSpawnEnv`, the `-p --output-format stream-json` ownership. A future reader who breaks any of these breaks the architectural contract — the comments are the documentation of *why* the body looks the way it does.

## Lessons learned

- **When extending a shared type, audit existing test helpers that build literals of it.** `test/dispatch/setupBranchAndWorktree.test.ts`'s `makeState` helper constructed a `DispatchState` literal with only the old two fields; the spec called this out explicitly and added the two-line fix to the ticket. Without that callout, the typecheck would have failed on a sibling test file. Generalisable rule: when widening a `readonly` interface that any test fixture builds literally, grep for `: <TypeName>` and `as <TypeName>` across `test/` before declaring the ticket scoped.
- **Test imports are allowed to be wider than module-body imports.** The test file imports `scrubSpawnEnv` and `SPAWN_ENV_DENYLIST` from `src/claude/spawn.ts` — that's how the test pins "reuses the real scrubber" without re-deriving the denylist. The architectural "no `src/claude/` import" rule is a module-*body* rule. Distinguish the two in future tickets so reviewers don't flag the wider test import.
