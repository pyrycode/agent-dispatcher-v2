# #59 — `src/loop/runAutoMerge.ts` per-cycle auto-merge with conflict rollback

Third file under `src/loop/`. Lands a maintenance routine (`runAutoMerge(deps) → Promise<void>`) that, each dispatch cycle, attempts to merge the ready PR attached to every Done-column item. On a `mergePr` conflict it rolls the ticket's project Status from `Done` back to `In Code Review`. Backstops the v1 #218 incident: without the rollback, the closed-sweep routine (#58) treats a Done item with an unmerged PR as terminal, and the selection pass silently re-dispatches closed work through stages it has already passed.

Sibling to `runDoneCleanup` (#57) and `runClosedSweep` (#58); same narrow-port shape.

## Surface

- `runAutoMerge(deps)` — async, no return value. Sequential `for...of`.
- `AutoMergeDeps = { listItems, listPrsForItem, mergePr, setItemStatusToInCodeReview }`.
- `AutoMergeItem = { id, issueNumber, status }` — minimal projection of `ProjectItem`. `id` is the project-item id (`PVTI_*`), used for the rollback mutation; `issueNumber` is what the future `listPrsForItem` helper keys on.
- The runner imports `findReadyPrNumber` and `ReadyPrCandidate` directly from `src/pipeline/find-ready-pr.ts` — first caller of that pure predicate, as `find-ready-pr.ts` anticipated.

## Behavior

Two predicate gates and one variant gate:

1. `item.status !== "Done"` → skip (non-Done items never enter the merge path).
2. `findReadyPrNumber(prs) === null` → skip (already-merged PRs aren't in the candidate list; drafts and error-labeled PRs filter out).
3. `result.merged === false && result.reason === "conflict"` → call `setItemStatusToInCodeReview(item.id)`. `reason === "other"` is intentionally NOT a rollback trigger.

`mergePr` returns a typed `MergeResult` discriminated union — conflict detection is never error-string parsing. Conflict surfaces as a typed value; transport / auth / rate-limit failures surface as `reason: "other"`.

## Why these contracts

### Rollback ONLY on `reason: "conflict"`, not on every `!merged`

`"other"` failures (transport, auth, rate limit) are transient — the next cycle retries automatically. Rolling back on `"other"` would create a thrash loop: the ticket bounces between Done and In Code Review every cycle while the underlying issue persists. Only the conflict variant represents a state a human reviewer needs to see. Per CLAUDE.md *"Don't write a defense for a failure mode that hasn't been observed"* — if `"other"` ever proves to keep a ticket permanently stuck in Done with an unmerged PR, retry / backoff lands as a follow-up.

### Narrow `setItemStatusToInCodeReview` port

Same posture as `runClosedSweep`'s `setItemStatusToDone`: the underlying client method is `setItemStatus(itemId, statusName)`, but the runner only ever moves to `"In Code Review"`. Closing over the status name at the launcher keeps the runner contract free of magic strings and keeps the test recorder shape one field per call (`{ itemId }`).

### `listPrsForItem` as a runner-level port (not pre-attached in `AutoMergeItem`)

No upstream `listPrsForBranch` / `listPrsForIssue` helper exists yet in `src/github/pr.ts`. Two alternatives the spec rejected:

- Widen `AutoMergeItem` with a `prs` field → forces this ticket to either expand into `src/github/pr.ts` (size violation) or embed an empty-array placeholder (defense for an unobserved failure mode).
- Compute PRs eagerly upstream → N+1 round-trips on every cycle for data only consumed when a Done item exists.

Keeping PR discovery as a separate port lets the listing helper land in the launcher ticket when it materializes. Done-column cardinality is small (terminal column + per-cycle cleanup), so the fan-out cost is bounded.

### Predicate stays inline; no `Column` import

`item.status !== "Done"` is one short-circuit and matches the precedent in `runClosedSweep` and `runDoneCleanup` — string literal in the runner, no `Column` type import. The rollback target `"In Code Review"` lives in the wiring closure, not in this file.

### Sequential, no `Promise.all`

Identical posture to the two sibling runners: Done-column cardinality is small; sequential keeps log order deterministic for tests and humans; the `mergePr → setItemStatusToInCodeReview` pair is one logical sub-step whose order must be preserved.

### No `try/catch`

`listItems`, `listPrsForItem`, `mergePr`, `setItemStatusToInCodeReview` errors propagate. A failure on item N aborts the sweep before N+1…M are processed. Acceptable because the runner is idempotent and the next cycle retries; failing fast surfaces real auth / rate-limit / project-misconfig issues rather than silently dropping work.

## Patterns established by this ticket

- **Discriminated `MergeResult` is the load-bearing invariant for conflict-handling code paths.** Consumers branch on `result.merged === false && result.reason === "conflict"`. Never parse error strings; never branch on `!result.merged` alone. New callers that surface conflicts to humans should follow the same dual-discriminant check — `reason: "other"` exists specifically to keep transient failures out of human-visible state changes.
- **`reason: "other"` is the "transient — let the next cycle retry" channel.** When adding new `MergeResult`-like discriminated unions for GitHub operations, reserve a non-rollback variant for transport / rate-limit / auth failures. Without it, idempotent retry policy ends up encoded as ad-hoc `try/catch` at every call site.
- **Maintenance-routine shape is now stable across three runners.** `runDoneCleanup` (#57), `runClosedSweep` (#58), `runAutoMerge` (#59) all share: narrow `Deps` interface, one port per I/O concern, closed-over status names, no `AbortSignal`, no retry, no `try/catch`, sequential `for…of`, predicate inline. The fourth runner (#60 rework routing) is expected to follow the same template.
- **First consumer of `findReadyPrNumber` confirms its split-from-a-shared-helper design.** The pure predicate ships in `src/pipeline/find-ready-pr.ts` for re-use between the dispatcher's loop (this ticket) and the salvage flow (later). No wrapper layer in `src/loop/` — the runner imports the predicate and its `ReadyPrCandidate` type directly.

## Lessons learned

- **Conflict surfacing belongs in project Status, not in labels.** A merge conflict on a Done item is a state change a human needs to see — and `In Code Review` is where review tooling and reviewer attention are already concentrated. Surfacing via a label instead would split human attention across two systems and would route through `decideLabelDelta` (which is for pipeline-stage transitions, not failure recovery). The rollback target picks the existing column, not a new "Merge Conflict" lane.
- **The maintenance-routine ordering inside the dispatch loop matters.** `runAutoMerge` must complete its rollbacks before `runClosedSweep` runs in the same cycle, otherwise a freshly-rolled-back Done→In-Code-Review ticket would not be observable from the closed-sweep predicate anyway, but a Done item whose merge silently failed earlier in the cycle would be incorrectly considered terminal. The loop ticket owns this ordering; this runner does not enforce it.
- **`MergeResult` had zero external consumers before this ticket.** `codegraph_impact MergeResult` confirmed only its own definition in `src/github/pr.ts`. Adding the second consumer (this runner) is additive — no signature changes anywhere — but future tickets adding callers should re-run the impact check before assuming the discriminant shape can be evolved freely.

## Out of scope (deferred to the loop / wiring ticket)

- **Retry / backoff on `reason: "other"`.** Owned by the loop layer if observation justifies it.
