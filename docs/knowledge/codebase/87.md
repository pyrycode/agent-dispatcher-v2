# #87 — `src/dispatch/handlePostRun` (happy-path callee arms `ready:<agent>`)

Dedicated happy-path function for the dispatcher's per-ticket flow. When `classifyAgentResult` (#86) returns `"ok"`, the orchestrator (a follow-up split from #77) calls `handlePostRun(state, deps)`; the function adds `ready:<state.agent>` on the issue and returns. The column does **not** change here — the add merely arms the forward auto-advance row that `decideAutoAdvance` fires on the next dispatcher cycle.

Sibling to [#88](88.md) (`handleDispatchError`). Same module shape, deliberate **inverse** error contract: `handlePostRun` propagates `addLabel` failures; `handleDispatchError` swallows them.

## Exports

### `src/dispatch/handlePostRun.ts`

- `HandlePostRunDeps` — `{ labels: Pick<GitHubLabelsClient, "addLabel"> }`. Only `addLabel` is needed; no logger, no project-board client.
- `handlePostRun(state: DispatchState, deps: HandlePostRunDeps): Promise<void>` — one-line body: `await deps.labels.addLabel(state.issueNumber, \`ready:${state.agent}\` satisfies Label)`.

Body shape: build the label literal with `satisfies Label`, single `await addLabel`. No try/catch (errors propagate); no `decideLabelDelta` call (see carve-out); no status I/O (column unchanged).

`DispatchState` is consumed unmodified — only `state.agent` and `state.issueNumber` are read. The interface was NOT extended.

## Why the carve-out, not a `TRANSITIONS` row

The post-run `ready:<agent>` add does not change the column, so no row of `TRANSITIONS` describes it. Three options were considered (full rationale in `docs/specs/architecture/87-handle-post-run.md`); the carve-out won:

- **Option A — degenerate same-column row.** Would shadow or be shadowed by the existing same-column rework rows (e.g. `In Architecture → In Architecture` requiring `needs-rework:architect`, `transitions.ts:104-108`); `decideLabelDelta`'s `find()`-by-`(from, to)` lookup can't disambiguate. Unworkable without changing `decideLabelDelta`.
- **Option B — `requires`-aware `decideLabelDelta`.** Would break `runDoneCleanup` (`src/loop/runDoneCleanup.ts:46-50`), which relies on the `In Documentation → Done` row being matched even when `ready:documentation` has already been stripped. Rejected.
- **Option C — carve-out.** Chosen. Mirrors the `wip:*` / `error:*` carve-outs documented at `src/pipeline/transitions.ts:37-41`, with one subtle adaptation: `ready:*` IS a member of the `Label` union. The carve-out here is **"this label-add isn't a transition-firing event,"** not "this label isn't a transition label." The forward row that later *consumes* the same `ready:<agent>` as a `requires` (e.g. `transitions.ts:80`) still funnels through `decideLabelDelta` when `decideAutoAdvance` fires, so the "transition-trigger label mutations funnel through `decideLabelDelta`" invariant holds for the column-changing mutation.

The module header pins this distinction explicitly. Reading it before adding any future `ready:*` site is mandatory.

## Why the error contract inverts vs. `handleDispatchError`

`handleDispatchError` (#88) swallows `addLabel` throws — its job is to keep the loop running after a failure. `handlePostRun` does the opposite:

| Outcome | Behaviour | Why |
|---|---|---|
| `addLabel` resolves | resolves void | `ready:<agent>` is on the issue; next auto-advance cycle moves the column |
| `addLabel` throws | rejects with the same error | orchestrator's outer try/catch routes to `handleDispatchError`, which tags `error:dispatch` |

Swallow-and-log would leave the ticket **without** `ready:<agent>` and **without** any visible marker — the agent-success would be silently discarded and the ticket would re-enter selection on the next cycle (no `wip:*`, no `ready:*`, no `needs-rework:*` ⇒ eligible) and run again. Propagation lights up the failure as `error:dispatch` for the next operator pass; rework routing strips `error:*` via `STRIP_PREFIXES` (`routing.ts:29`) when triaged. This is the simpler code path *and* the safer one.

## Why no classifier input

`classifyAgentResult` returns `"ok" | "agent-error"`. The orchestrator does the `cls === "ok"` test at the call site, where the discriminant is meaningful; the call into `handlePostRun` is the *consequence*, not the condition. Passing the literal `"ok"` adds zero information to the body, and the full `StreamParseResult` adds none either — the body only needs `state.agent` and `state.issueNumber`. Signature is `(state, deps)`, narrowest shape this phase actually reads.

## Why no status mutation

The project-board Status field mirrors the column. Column unchanged ⇒ Status unchanged ⇒ no `GitHubProjectClient` dep is injected. The `HandlePostRunDeps` interface is intentionally smaller than `HandleDispatchErrorDeps` (no logger, no project client) — each callee takes only what it actually touches.

## Patterns established

- **Sibling callees with inverted error contracts must be readable as a pair.** `handlePostRun` (propagate) and `handleDispatchError` (swallow) are structural mirrors — same `(state, deps)` shape, same `Pick<GitHubLabelsClient, "addLabel">` dep, same carve-out-cited header — diverging only on the rethrow vs. swallow axis. The module headers each state which side they're on; the test files pin it via `.rejects` (this ticket) vs `.resolves` (#88). When adding a third dispatcher-side callee, follow the pair: pick a side, state it in the header, pin it with the matching assertion. Don't mix the contracts within one function.
- **`satisfies Label` on a template-literal-constructed label is the compile-time trip-wire for "agent union and ready:* union must stay in sync."** `` `ready:${state.agent}` satisfies Label `` makes adding a new `Agent` member without adding its `ready:*` to the `Label` union a type error at this site. Pattern transfers to any future location where a label literal is constructed from an `Agent`: prefer `satisfies` over a plain `const x: Label = …` annotation — `satisfies` preserves the literal type while still asserting assignability, so refactors that widen the variable type don't silently lose the guarantee.
- **The "carve-out from `decideLabelDelta`" rule has TWO flavours now, and the header must say which.** Flavour 1 (`wip:*` / `error:*`, `src/salvage/draft-pr.ts`, `src/dispatch/handleDispatchError.ts`): the label is dispatcher state, not in the `Label` union at all. Flavour 2 (this ticket): the label IS in the `Label` union — it's a transition trigger — but THIS particular add isn't the transition-firing event; the forward consumer is. Future `ready:*` / `needs-rework:*` add sites that don't change the column fall into flavour 2; future `wip:*` / `error:*` / metadata sites fall into flavour 1. Headers in both flavours cite `src/pipeline/transitions.ts:37-41` plus, for flavour 2, the consuming forward row line number.
- **Callee dep interfaces should shrink to what the body touches, even if a wider client exists.** `HandlePostRunDeps` is `{ labels: Pick<GitHubLabelsClient, "addLabel"> }` — no logger (this phase doesn't log), no project client (column doesn't change). The launcher wires the full clients at the edge; the callee accepts the slimmest projection. Pattern: prefer `Pick<X, "methodA" | "methodB">` over `X` in dep interfaces, and drop dep fields entirely when the body doesn't use them.
- **Reuse the sibling's test scaffolding verbatim when the shapes line up.** `fakeLabels({ onAdd })` and `makeState(overrides?)` were lifted from `test/dispatch/handleDispatchError.test.ts` and dropped in with the logger plumbing removed. Pattern: when a new test file's unit-under-test shares a dep shape with an existing sibling, copy the helpers literally — divergence in fakes between siblings makes drift in the production contracts harder to spot.

## Lessons learned

- **The architect's "narrowest shape this phase actually reads" heuristic prunes seams aggressively.** Two seams were left open by the PO ticket — classifier-input shape and status-mutation dep. Both resolved to "nothing": no classifier input (the orchestrator's call-site test is the discriminant; passing it through would be ceremony), no `GitHubProjectClient` dep (column doesn't change, so Status doesn't either). Pattern: when a seam is flagged, the first question is "what does the body need to read?" — if the answer is "nothing from this input/dep," the seam closes by deletion, not by picking a flavour.
- **Three-tests-pin-every-AC-bullet is achievable when the function body is one expression.** AC bullets covered by the three tests: exported from `src/dispatch/`, takes `(state, deps)`, applies post-run label via injected I/O (tests 1+2); unit tests cover happy path + label-add observed on fake (tests 1+2); status change "if any" recorded (no dep, documented null). The static ACs (no `src/github/` value-import, carve-out documented in header, ≤100 lines) are pinned by review on commit, not by tests. When the function body is ≤2 expressions, exhaustive runtime tests are cheap; lean on them.
