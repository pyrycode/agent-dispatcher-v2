# #69 — `src/salvage/gate.ts` `shouldAttemptSafeSalvage`

First file under `src/salvage/`. Pure decision module that answers "should the dispatcher open a draft PR with a `max_turns` agent's partial work for human review?" by running every operator-configured gate command and returning `true` only if all exit 0.

## Exports

- `GateRunner = (cmd: string) => Promise<number>` — DI seam. Resolves to the command's exit code; the orchestrator's wrapper translates spawn failures to a sentinel non-zero code (e.g. `127`) so the runner never throws on normal "gate failed" paths.
- `parseSalvageGates(raw: string | undefined): readonly string[]` — splits on `/[,;]/`, trims, drops empties, freezes the result. Exported separately so a future `--print-gates` debug surface (or a test) can inspect parse output without going through the async path.
- `shouldAttemptSafeSalvage(gates, run): Promise<boolean>` — `parseSalvageGates` → empty parse returns `false` (unset / `""` / whitespace-only / all-empty-segments) → otherwise `for` loop awaiting each `run(cmd)` and returning `false` on the first non-zero. Returns `true` only when every gate exits 0.

## Why the runner is injected

Salvage lives under `src/salvage/`, not `src/pipeline/`, but CLAUDE.md's "Pure functions, I/O at the edges" rule applies all the same: the decision module has no `node:child_process` import anywhere in its dependency closure. The runner is passed in. Tests use an in-process fake (`recordingRunner`) — `test/salvage/` has zero subprocess plumbing. The orchestrator (later ticket) supplies a real wrapper around `execFile` or `spawn`.

## Short-circuit on first failure

The AC permits either ordering (short-circuit vs. run-all). Sequential short-circuit is the cheaper default: typecheck failing means there is no point burning CPU on the test suite. Parsed-command order matches the operator's env-var order, so operators put the cheapest gate first. Pinned by tests: `recordingRunner` records call sequence and the "first gate fails" case asserts the second runner is never invoked.

## Empty-parse → `false`, deliberately

An empty `SALVAGE_GATES` env var (unset, `""`, `"   "`, or `",,;;"`) yields an empty parsed list and `shouldAttemptSafeSalvage` returns `false` — **not** `true`. This is the contract [ADR 0002](../decisions/0002-salvage-gates-default-empty.md) flagged when it set the default to empty: "the salvage module MUST treat an empty gate list as 'no gates configured' and decide its own policy — likely 'salvage disabled' rather than 'zero gates means everything passes.'" That decision is now ratified in code.

## Error handling: no try/catch

- Runner resolves non-zero → normal "gate failed" → `false`.
- Runner throws → rejection propagates to the caller. Deliberate: a throwing runner is a bug in the orchestrator's wrapper, not a gate failure. Swallowing would silently re-interpret a programming error as "all gates passed" — exactly the wrong direction for a safety gate.

## Parser drift with `env.ts`

`src/config/env.ts:56-64` also parses `SALVAGE_GATES`, but splits on `;` only and produces `Config.salvageGates: readonly string[]`. This module's parser handles both `,` and `;`. Two parsers now exist for the same env var.

**Intended end state:** the salvage orchestrator (later ticket) passes the **raw** env value to `shouldAttemptSafeSalvage`, not `Config.salvageGates`. `salvageGates` on `Config` becomes dead. Resolution options for the orchestrator's architect to pick:

- (a) Drop `salvageGates` from `Config`; orchestrator reads raw `SALVAGE_GATES` directly. Cleanest.
- (b) Widen `env.ts`'s parser to also split on `,`. Two parsers but consistent.
- (c) Accept the drift; this module is the source of truth, `Config.salvageGates` becomes dead.

This ticket landed (a)'s contract (`gates: string | undefined`) but did not delete `Config.salvageGates` — that touches `env.ts` and is out of scope.

## Shell semantics are out of scope

The runner is DI'd, so this module doesn't care how commands execute. The orchestrator's wrapper picks `spawn(cmd, { shell: true })` vs. `execFile` — pipes/redirects/env interpolation vs. argv-safer. Decided in the orchestrator spec, not here.

## Patterns established

- **DI'd subprocess runner as the pure/edge seam for non-pipeline modules.** The "I/O at the edges" rule is not exclusive to `src/pipeline/` — `src/salvage/` follows the same shape: the decision module takes `(cmd) => Promise<number>` and the orchestrator binds the real `child_process` call at the seam. Reuse this for any future `src/salvage/`, `src/worktree/`, `src/claude/` decision module whose async path is dominated by one subprocess primitive.
- **Export the parser separately from the decision.** When a decision wraps a small parser, export the parser too. It pins parse cases in tests without async noise and gives future debug surfaces a side door. Mirrors the `parseConfig` / `loadConfig` split in `src/config/env.ts`.
- **Empty configuration ≠ permissive.** When an env var defaults to empty (per [ADR 0002](../decisions/0002-salvage-gates-default-empty.md)), the consuming module's policy must be "disabled," not "everything passes." Pinned for `SALVAGE_GATES`; the same shape should apply to any future opt-in safety gate.
- **No defensive try/catch around an injected port.** A throwing port is a caller bug. Let the rejection propagate; do not convert it into a `false` that masks the bug as a benign "gate failed."

## Out of scope (deferred follow-ups)

- The salvage orchestrator — calls `shouldAttemptSafeSalvage`, decides what to do with the verdict, owns the real `child_process` wrapper, owns wall-clock budgeting + any `AbortSignal` plumbing.
- Reconciling the two `SALVAGE_GATES` parsers (`env.ts` vs. this file) — flagged for the orchestrator's architect run.
- `spawn` vs. `execFile` choice for the real runner wrapper.
- Timeout / abort on individual gate commands.
- Parallel gate execution — short-circuit-on-first-failure dominates the typical "typecheck then test" ordering; revisit only if a consumer reports gates that benefit from parallelism.
