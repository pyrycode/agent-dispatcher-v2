## Patterns established

### Configuration loading (#3)

- `src/config/env.ts` is the single source of truth for env vars. Downstream modules consume the typed `Config` via constructor injection — no `process.env` reads outside this file.
- Pattern: pure `parseConfig(env)` core + thin `loadConfig({ agentsRoot })` I/O wrapper. Same shape as `paths/` resolvers — branch tests target the pure function.
- **Empty-string env values are treated as unset** in BOTH `.env` AND `process.env`. The `loadConfig` merge filters empties out of `process.env` before layering, so an explicit `KEY=""` in the launcher's shell does not silently nuke `.env` values.
- **`process.env` overrides `.env`** for any key with a non-empty value (CI / test harness can inject overrides). `.env` provides the developer's local defaults.
- **`GITHUB_TOKEN` value never appears in error messages** — module only validates non-empty (no shape check) so no error path can echo it. Lock-in test in `test/config/env.test.ts` (`token redaction` describe block) is the canary; any future shape-validation must preserve this.
- Returned `Config` is `Object.freeze`d (runtime guard) plus every field is `readonly` (compile-time guard). `salvageGates` is a frozen `readonly string[]`.
- `SALVAGE_GATES` defaults to `[]` (salvage opt-in) — see [ADR 0002](knowledge/decisions/0002-salvage-gates-default-empty.md).

### CI plumbing (#1)

- Single workflow file at `.github/workflows/ci.yml`. One job, one OS (`ubuntu-latest`), one Node major (22). No matrix unless explicitly required.
- Four steps in order, each its own `- run:`: `pnpm install --frozen-lockfile`, `pnpm typecheck`, `pnpm test`, `pnpm lint`. Don't chain with `&&` — named step boundaries surface failures cleanly.
- `pnpm/action-setup@v4` runs **before** `actions/setup-node@v4`. setup-node's `cache: 'pnpm'` invokes pnpm to resolve the store path; reversing the order produces "pnpm: command not found".
- Node version comes from `package.json#engines.node` via `node-version-file: 'package.json'`. pnpm version is pinned in the workflow YAML (`version: 9`) — see [ADR 0001](knowledge/decisions/0001-pnpm-version-in-workflow.md).
- `concurrency` cancels superseded runs on the same ref. `permissions: contents: read` only.
- New CI checks are added as a new `- run:` step. Don't bundle into existing steps.

### src/pipeline/ purity (#6)

- Files under `src/pipeline/` are pure: no `await`, no `gh` / `git` / `fs` calls, no shared state. Inputs are POJOs supplied by callers; outputs are decisions. Tests live in `test/pipeline/<name>.test.ts` and exercise the predicate in isolation — no integration target until a `src/dispatch/` consumer lands.
- Input types are defined in the same file as the predicate (e.g. `Blocker`, `BranchState` in `blockers.ts`). They are intentionally narrow — only the fields the predicate reads. Richer GitHub shapes are narrowed at the `src/github/` boundary before being handed to the predicate. Don't widen for hypothetical future consumers.
- `shouldFlagEmptyBranch` distinguishes silent failure (`commitsAhead === 0`, no `needs-rework:*` label → flag for `error:*`) from deliberate bail (`commitsAhead === 0`, `needs-rework:*` present → label routing already handles it). The four-row ambiguity matrix in `test/pipeline/blockers.test.ts` is load-bearing — one assertion per row so a regression points at the exact failing row.
- `parseCommitsAhead` throws on malformed input rather than returning `-1` / `null` — the dispatcher catches at the I/O boundary. Use a `/^\d+$/` regex over `parseInt` to avoid silent truncation of inputs like `"5abc"`.
- `shouldProduceCommits(agent, action)` is the explicit table of which agent-runs must produce commits. Exhaustive `switch` on `AgentName` (no `default`) gives a TS error when a new agent is added — load-bearing exhaustiveness check.
- Helpers stay unexported until a second consumer appears (e.g. `hasNeedsReworkLabel`). Promoting preemptively buys nothing and adds API surface to refactor when the rule generalizes.
- Policy thresholds from `CLAUDE.md` (e.g. `XS_MAX_PRODUCTION_LINES = 30`, `S_MAX_PRODUCTION_LINES = 100` in `sizing.ts` (#25)) are exported as named constants and pinned by their own test assertions. The constant-pinning tests sit alongside boundary-pinning tests — if a future change drifts both the constant and the boundary cases in lockstep, the constant assertion still anchors the policy value. Any predicate that encodes a CLAUDE.md-documented number should follow this shape.
- Set-intersection-style predicates (e.g. `fileOverlapsAny` in `sizing.ts` (#25)) use exact string equality. No path normalization, case folding, or glob matching inside the predicate — caller canonicalises at the I/O boundary. Add normalization only when an observed real-world mismatch demands it.

### Transition table (#24)

- `src/pipeline/transitions.ts` is **data only** — no functions, no logic. Four exported types (`Column`, `Label`, `LabelPattern`, `Transition`) and two exported constants (`COLUMNS`, `TRANSITIONS`). Consumers (`decideLabelDelta` in #5, rework routing in #7) import directly; no `src/index.ts` re-export.
- `Label` and `LabelPattern` are intentionally narrow per the #6 narrow-types rule — only labels that some transition's `requires` actually consumes are members. `wip:*`, `error:*`, `size:*`, `priority:*`, `security-sensitive` are dispatcher-run lifecycle / metadata, not transition triggers, and stay out until a transition consumes one. Widen at that point, not preemptively.
- `LabelPattern` (`"ready:*"`, `"needs-rework:*"`) is a closed set with the same narrow-types rule: only patterns whose underlying labels can actually gate a transition belong here. The dead-letter test (`strips` patterns must match a label produced by some `requires`) is what enforces it.
- **Same-column rework rows are deliberate, not bugs.** `In Architecture → In Architecture` (and the developer / code-review variants) appear because the column doesn't change but the labels do, and `decideLabelDelta` is the only place labels mutate. Without these rows, #5 would have to special-case label-only transitions outside the table.
- **`Inbox → Backlog` row has empty `requires`.** It's a manual human-triage move. Without it the reachability test fails for every column except Inbox, since nothing else routes out of Inbox.
- Forward auto-advance rows have empty `strips` (matches v1's `runAutoAdvance` "no strip" semantics). Done + rework rows strip `ready:*` + `needs-rework:*` so the target re-runs on a clean slate.
- Three invariant tests in `test/pipeline/transitions.test.ts` are the verification: reachability from Inbox, `from`/`to` membership in `Column`, and no dead-letter `strips` patterns. There's no integration target — consumers land in their own tickets and get behavioral tests there.
- No `needs-rework:documentation` row(s) yet — no observed transition routes back into documentation as a rework target. If a future ticket needs it, widen the `Label` union and add the row.

### src/pipeline/ selection (#30)

- `src/pipeline/selection.ts` lands the `selectDispatches.cap` term of CLAUDE.md's throughput equation. Pure function: walks `state.items` in caller-supplied order, skips ineligible (wip:* / open-blocker / non-consumed-column), early-`break`s at `result.length >= maxConcurrent`. `maxConcurrent <= 0` short-circuits to `[]` — no-op on negative input matches v1's permissive shape.
- `Agent` (column-consumer union) is **distinct from `AgentName`** in `blockers.ts` (commit-producer union) by design. `Agent` includes `"po"` (Backlog consumer); `AgentName` excludes it (PO triages, doesn't run with a worktree). Per the #6 narrow-types rule, each pipeline module owns its narrow type for its narrow concern. Two parallel narrow unions overlapping by four members is correct, not duplication — promote to a shared union only when a third caller genuinely needs both.
- `AGENT_COLUMN_MAP` is encoded as data, not derived from `TRANSITIONS`. "Label gates this transition" and "agent consumes this column" are distinct concerns; deriving would couple a future label rename (e.g. `ready:po` → `triaged:po`) into selection. Inbox and Done are absent — items in those columns have no consuming agent and are silently skipped (Inbox→Backlog is manual human triage; Done is terminal).
- `DispatchTuple` is minimal `{ agent, issueNumber }`. The dispatcher builds the worktree from the issue number — widening to the full `SelectionItem` would speculate on a hypothetical future consumer (the loop module hasn't landed). If a downstream caller needs more, it has the original `state.items` array in scope.
- Per-issue label scoping is **structural**: each loop iteration reads only `item.labels` / `item.blockers`, so item B's labels are physically out of scope when deciding item A. The paired tests (gated A + ungated B → result contains only B) verify this.
- `hasWipLabel` is prefix match (`startsWith("wip:")`), mirroring `hasNeedsReworkLabel` in `blockers.ts`. Regression-tested: `something-wip:bar` does NOT trigger. Same shape rule established in #6 — substring matches are bug magnets.
- `isEligible` is the one place gates compose; new pipeline gates add a line there. Stays unexported until a third consumer (beyond `selectDispatches`) appears.
- `selectDispatches` does NOT throw on items in unmapped columns (Inbox, Done) or on items missing labels/blockers — TypeScript types are the contract; defensive `?? []` widening would mask caller bugs at the I/O boundary. Same stance as `blockers.ts`.

### src/pipeline/ rework routing (#31)

- `src/pipeline/routing.ts` is the routing half of `src/pipeline/` — sibling to `decideLabelDelta` (#5) and `selectDispatches` (#30). Pure function `decideReworkRouting(labels): { target, stripLabels }`. Mirrors v1's `runReworkRouting` strip contract: when a reviewing agent flags `needs-rework:<target>`, the function returns the agent to re-run plus every `ready:*` / `wip:*` / `error:*` label currently on the ticket, so the target runs on a clean slate.
- **`Agent` is derived from `Label` via template-literal `infer`** (`type ExtractAgent<L> = L extends 'needs-rework:${infer A}' ? A : never`). Single source of truth on `Label` in `transitions.ts`. Adding `needs-rework:documentation` (etc.) to `Label` widens `Agent` automatically — no second site to update. Today: `"po" | "architect" | "developer" | "code-review"`.
- **Three narrow `Agent`-flavoured types coexist** by design — this module's `Agent` (rework targets), `selection.ts`'s `Agent` (column consumers, includes `"documentation"`), and `blockers.ts`'s `AgentName` (commit producers, excludes `"po"`). Per the #6 narrow-types rule, each pipeline module owns its narrow type for its narrow concern; promote to a shared union only when a fourth caller needs the union of two. The string-drift cost is bounded by all three files staying small and pure.
- **Input is `readonly string[]`, not `readonly Label[]`.** `wip:*` and `error:*` are intentionally absent from the narrow `Label` union (they're dispatcher run-state, not transition triggers). This function is the boundary where dispatcher state crosses a pure predicate; widening `Label` would break the dead-letter invariant in `decideLabelDelta`'s tests.
- **`needs-rework:<target>` is NOT in `stripLabels`.** The dispatcher consumes it downstream when promoting to `wip:<target>`; stripping here would race against that promotion. The filter explicitly excludes the captured rework label even though it begins with a strip-eligible-looking prefix.
- **Why this is separate from `decideLabelDelta` (#5).** `decideLabelDelta` strips `ready:*` and `needs-rework:*` per the transitions table but does NOT touch `wip:*` / `error:*` (not transition triggers). Rework routing is the only place that surfaces them, so it owns the strip list. The two compose at the dispatcher seam.
- **Multiple `needs-rework:*` labels — first by input order wins.** Pinned by test so a future drift surfaces. Normal-path invariant (`≤1 needs-rework:*`) is enforced upstream by `decideLabelDelta`'s strips; this function does not re-validate.
- **Malformed bare `needs-rework:`** (empty suffix) is treated as not-a-rework-label. Closed `Label` union has no empty-suffix member; silent ignore routes through the no-op path rather than crashing the loop. Per CLAUDE.md § "Don't write a defense for a failure mode that hasn't been observed", no runtime validation against `Agent`'s literal set.
- **Structural invariant test** iterates a hand-listed `REWORK_LABELS` const tuple (TS literal types erase at runtime). Comment references `transitions.ts:48-51` so the next contributor knows where to mirror a new entry. If `Agent`'s derived literal set drifts from the test fixture, the invariant fails the suite.

### src/github/ I/O surface (#19)

- `src/github/` is the I/O edge for GitHub Projects v2. `project-client.ts` is the single initialization surface; sibling files (`issues.ts` in #20, `labels.ts` in #21) and the loop will receive a `GitHubProjectClient` via DI rather than reaching for a global. No file under `src/pipeline/` may import from `src/github/` — that direction is the seam between pure decisions and live state.
- **Static factory + private constructor.** `GitHubProjectClient.initialize(opts, transport)` is the only entry point; the constructor is private. The factory resolves project ID + Status field ID + Status option IDs up front so methods can rely on the cached state without `if (!projectId) throw "Not initialized"` defensive guards. Mirrors the `parseConfig` / `loadConfig` split — the wrapper makes a precondition unfakable.
- **Transport is dependency-injected as a callable.** `type GraphQLTransport = (query, variables) => Promise<unknown>` mirrors `@octokit/graphql`'s exported callable shape. Production wiring (later ticket) is one line: `graphql.defaults({ headers: ... })`. Tests hand-roll a routing-table function — no mock library, no inheritance, no `as any`. The `calls` log is the verification mechanism for "transport receives the right query".
- **No `@octokit/graphql` runtime dep here.** The transport is interface-shaped; the launcher decides on the implementation. Adding the dep happens only when the production transport lands — keeps this module zero-dep, the integration tests zero-network, and a future swap (e.g. to `gh api graphql`) costless.
- **Org-aware dispatch is explicit; NO try/catch fallback.** `ownerType === "organization"` interpolates `organization(login:)`; `"user"` interpolates `user(login:)`. A mismatched `ownerType` propagates the GraphQL error verbatim — wrapping it in a `try { /* org */ } catch { /* user */ }` fallback would mask every auth / rate-limit / transient failure as "wrong owner type". Test #3 locks both the verbatim message AND `transport.calls.length === 1`.
- **Native ordering, never derived from `issueNumber`.** Items are fetched via `orderBy: { field: POSITION, direction: ASC }`; the result array is returned in transport order. Sorting client-side by `issueNumber` would put split-children out of order (PO inserts at the top, lower numbers naturally) and break the dispatcher's "drag to prioritize" affordance. Test #4 has a `.not.toEqual([10, 20, 30, 50])` regression guard against any future "sort for test stability" simplification.
- **`ProjectItem` is intentionally narrow** — `id`, `issueNumber`, `title`, `status`, `labels`, `url`. Per the #6 narrow-types rule, do NOT widen for hypothetical future consumers. Sibling tickets (#20 issues, #21 labels) widen at the moment they need a field.
- **`status` is a `string` with `"no-status"` sentinel** when `fieldValueByName` is null. Keeps consumer types simple (`string`, not `string | null`) and matches v1. Boards with un-statused items still list cleanly.
- **Pagination is in this ticket; cap is fixed.** `MAX_PAGES = 50` (5000 items). v1 #203 was the precedent — a single `items(first: 100)` truncated boards past 100. The cap is the regression guard against the next variant (echoed `endCursor`, broken `hasNextPage`); it throws with a message that names the failure mode rather than silently consuming the GraphQL budget.
- **Per-cycle items cache + rate-limit tracking are NOT here.** Both observed in v1 but layered at the loop boundary — caching conflates I/O with policy, rate-limit tracking belongs where the loop's per-cycle budget is. Add a caching adapter when the loop module lands; add rate-limit tracking when budget pressure is observed.
- **GraphQL queries are minified single-line strings.** Multi-line indented queries pushed the file past the 200-line hardcap. They're opaque to the rest of the system; readability lives in the test fixtures and the surrounding comments.

### src/github/ issues REST surface (#35)

- `src/github/issues.ts` is the second file under `src/github/` — issue-level read/write wrappers (`getIssue`, `createIssue`, `updateIssue`) over `/repos/{o}/{r}/issues`. Sibling to `project-client.ts` (#19); consumers (loop, rework flows) wire in via DI in later tickets. No file under `src/pipeline/` may import from `src/github/`.
- **`RestTransport` is a parallel DI seam to `GraphQLTransport`.** `(method: "GET" | "POST" | "PATCH", path, body?) => Promise<unknown>` mirrors the callable shape of `gh api -X <method> <path>` or `@octokit/rest`'s callable. Production wiring is one-line at the launcher; tests hand-roll a routing-table function (`(method, path, body)` matcher + `calls` log). The launcher will wire BOTH transports — REST and GraphQL pick the right tool per endpoint, not per ticket. A future consolidation behind a unified `GhApiTransport` is a non-breaking refactor at the launcher seam.
- **REST over GraphQL for issue mutations is deliberate.** REST's `PATCH /repos/{o}/{r}/issues/{n}` takes `labels: string[]` natively (no node-ID resolution), supports replace-set semantics in one call, and keys on `(owner, repo, number)` directly. GraphQL would require an extra labels-by-name query plus add/remove deltas plus a number→nodeId resolution before each mutation. For a "thin wrapper," one call is the right cost.
- **Static factory + private constructor.** `GitHubIssuesClient.create({ owner, repo }, transport)` is the only entry point (synchronous — REST endpoints take `(owner, repo, number)` directly, so there's nothing to resolve up front, unlike #19). The class binds `(owner, repo, transport)` once; consumers see `client.getIssue(123)` with the context implicit. Free functions would fan the DI triple across every call site.
- **`updateIssue` patch shape: `!== undefined`, not truthiness.** `if (patch.body !== undefined)` is load-bearing — callers can legitimately pass `body: ""` to clear the body, or `labels: []` to drop all labels. A `if (patch.body)` truthiness check would silently drop those updates. Test #7 (`body: ""` IS a real update) is the regression guard.
- **`updateIssue(n, {})` resolves to `null` without a transport call.** AC: "Omitting both is a noop, not an error." Test #6 locks BOTH the resolved value AND `transport.calls.length === 0` — either alone is forgeable.
- **No `labels: undefined` leakage in PATCH bodies.** Conditionally building the request body (`if (patch.labels !== undefined) body.labels = ...`) is load-bearing because GitHub's REST PATCH replaces the full label set. A leaked `labels: undefined` (or empty array) would silently strip every label off the issue. Test #3 deep-equals the request body as the canary.
- **`Issue` is intentionally narrow** — `number`, `title`, `body`, `labels`, `state`, `url`. Same #6 narrow-types rule as `ProjectItem`. No `assignees` / `milestone` / `closedAt` until a consumer needs them.
- **`body: null` from GitHub is mapped to `""`.** Keeps `Issue.body: string` (not `string | null`). Same posture as `status: "no-status"` sentinel in #19 — narrow types over null-juggling at every call site.
- **No `@octokit/rest` runtime dep here.** Transport is interface-shaped; the launcher provides the implementation. `package.json` unchanged. Same posture as #19.
- **Standalone `addLabel` / `removeLabel` helpers are deferred.** Callers compose via `updateIssue`'s `labels` patch (read-modify-write via `getIssue`). v1 had them as separate primitives; v2 hasn't observed a delta-style call site that doesn't first read.
- **Per-issue cache, retry/backoff, rate-limit tracking are NOT here.** Same boundary as #19 — caching belongs at the loop layer; resilience policy lives in the transport implementation.

### src/github/ blocked-by primitive (#37)

- `src/github/blocked-by.ts` is the third file under `src/github/` — a single GraphQL `addBlockedBy` mutation wrapper exported as a free function `addBlockedBy(blockedNodeId, blockerNodeId, transport)`. Pairs the architect-flow split's "set the dependency" prose with a deterministic primitive (CLAUDE.md "Belt-and-suspenders") that the dispatcher's `hasOpenBlockers` predicate (#6) reads via the native sub-issue relationship.
- **Free function, not a class.** No state to cache, no precondition to protect — `project-client.ts` (#19) and `issues.ts` (#35) are classes for state-binding reasons (resolved IDs / `(owner, repo)` binding); this isn't one. A `BlockedByClient.create(transport)` factory would buy zero semantic gain. If a future ticket binds `(transport)` once across many call sites, a thin adapter is a non-breaking addition.
- **Role mapping is load-bearing.** The GraphQL mutation's `issueId` input is the **blocked** issue; `blockingIssueId` is the **blocker**. Argument names spell the roles in plain English (`blockedNodeId` / `blockerNodeId`) so call sites read unambiguously. Test #1 deep-equals the transport variables — `{ issueId: blockedNodeId, blockingIssueId: blockerNodeId }` — to pin the mapping; a future "swap these for symmetry" simplification would set the dependency the wrong way around and break this assertion immediately.
- **Takes node IDs, not issue numbers.** The GraphQL mutation requires node IDs natively; a hidden number→nodeId resolution inside this primitive would add a round-trip the call site can't see. Callers with only numbers compose with `src/github/issues.ts` (#35) before calling here. Same "narrow types at the boundary" posture as #6 / #19.
- **`Promise<void>` return shape.** The mutation's `issue { number }` selection set is a sanity round-trip the GraphQL API forces (`addBlockedBy(...) { ... }` requires a non-empty selection); the response is intentionally discarded. Absence of a thrown error IS the success signal — surfacing the number would speculate on a hypothetical caller.
- **Errors propagate verbatim — no try/catch, no fallback retry, no message rewriting.** Invalid node IDs surface the canonical GraphQL error (`Could not resolve to a node with the global id of '...'`) intact. Test #2 locks BOTH the canary substring AND `transport.calls.length === 1`; a future PR that adds a try/retry shim either updates this assertion (visible in the diff) or breaks it (caught in CI).
- **Imports `GraphQLTransport` from `project-client.ts`** — single source of truth for the DI seam. Sibling-module imports inside `src/github/` are explicitly fine (CLAUDE.md "no barrels" forbids `src/index.ts` re-exports, not direct sibling imports). When a third GraphQL consumer appears, promote `GraphQLTransport` to `src/github/transport.ts`.
- **Mutation as a top-level minified `const`.** Mirrors the `INIT_QUERY` / `ITEMS_QUERY` shape in `project-client.ts:47-50` — groups all GraphQL strings at the top of the file; minification dodges the 200-line hardcap consistently across the directory.
- **No `removeBlockedBy`, no `blockedBy(issueNodeId)` query helper, no `@octokit/graphql` dep.** Same posture as #19 / #35 — defer until an observed call site appears. The dispatcher already reads the relationship via `hasOpenBlockers` (#6) over a `Blocker[]` shape supplied by the I/O layer; the fetch belongs in #20 or as a sibling primitive when its consumer lands.

### src/github/ labels REST surface (#36)

- `src/github/labels.ts` is the fourth file under `src/github/` — three label-mutation primitives (`addLabel`, `removeLabel`, `setLabels`) over `/repos/{o}/{r}/issues/{n}/labels`. This module makes no decisions; the pure pipeline (`decideLabelDelta`, #5) does. The class binds `(owner, repo, transport)` once via `GitHubLabelsClient.create`, mirroring `GitHubIssuesClient` (#35) and `GitHubProjectClient` (#19).
- **`addLabel` THROWS on transport failure — load-bearing.** The salvage flow (#12) applies `error:max_turns_salvaged` BEFORE `gh pr create`; a swallowed-error `addLabel` would produce a labeled-PR-without-label that gets re-dispatched on the next cycle as a normal ready PR. CLAUDE.md "Belt-and-suspenders" — the deterministic transport-level safety net behind the agent's "remember to add the label" prose. Test #2 (`addLabel transport-failure THROWS`) is the canary.
- **`addLabel` does NOT skip-when-already-present.** A "skip POST when cached as present" optimization would open a window where an externally-removed label silently isn't re-added — exactly the salvage failure mode. POST is one call; GitHub dedupes server-side. The asymmetry with `removeLabel` (which DOES skip when absent) falls out of the cost ranking: addLabel's failure mode is silent dispatcher bug, removeLabel's is cosmetic mutation.
- **`removeLabel` is idempotent via GET-then-PUT-only-if-present, NOT via `DELETE` + 404-catch.** GitHub's `DELETE /labels/{name}` returns 404 when absent, which the transport contract throws on. Inspecting error shape (`error.status === 404`?) for idempotency would couple the wrapper to a transport implementation detail the contract intentionally doesn't expose. Read-modify-write keeps the transport opaque; idempotency falls out of the filter. Test #4 (no PUT route registered when label is absent) is the regression guard against any "always PUT for symmetry" simplification.
- **All three methods target `/issues/{n}/labels` (NOT `/issues/{n}` with the `labels` patch field).** That patch field is `updateIssue`'s concern (#35); mixing both paths would double the test surface for no behavioral gain. One path template, three verbs (POST / GET / PUT) — endpoint family consistency.
- **`labels: undefined` leak ruled out by construction.** `setLabels`'s parameter is `readonly string[]` (not `... | undefined`); body is built unconditionally as `{ labels: names }`. `removeLabel`'s PUT body is `{ labels: next }` where `next` is a `.filter()` result. `addLabel`'s POST body is `{ labels: [name] }`. The deep-equals assertions on recorded request bodies in tests are the canaries (lessons.md #35 PATCH replace-set lesson, generalized to PUT).
- **`setLabels(n, [])` sends `{ labels: [] }` — strips every label.** Pass-through to the pure pipeline's decision; this module doesn't second-guess it. Test #6 deep-equals the body.
- **All three methods return `Promise<void>`.** Callers don't read the post-write label list; returning would force a narrow-shape decision and add API surface. Widen at the moment a consumer needs it.
- **`mapLabels` defaults to `[]` on shape drift, never throws.** Mirrors `mapIssue`'s field-level type-guard posture (#35). Response-validation belongs at the transport boundary.
- **`RestTransport` union widened by one literal (`"PUT"`).** PO's technical note explicitly green-lit this. No call-site cascade — existing callers (`getIssue` / `createIssue` / `updateIssue`) all pass one of the original three literals; widening is additive.
- **No `addLabels` / `removeLabels` plural primitives, no `listLabels` public read helper, no `DELETE /labels/{name}` wrapper, no `@octokit/rest` runtime dep.** Same posture as #19 / #35 — defer until an observed consumer needs the shape.

### src/github/ PR I/O surface (#41)

- `src/github/pr.ts` is the fifth file under `src/github/` — three thin PR-surface I/O ops (`createPr`, `enableAutoMerge`, `mergePr`) over the GraphQL transport. `GitHubPrClient.initialize({ owner, repo }, transport)` resolves the repository node ID up front so methods rely on cached `repositoryId`. Mirrors `GitHubProjectClient.initialize` (#19).
- **`mergePr` returns conflict as a typed value, NOT a thrown error — load-bearing.** The ticket exists solely for this contract. v1 lesson 2026-05-09 evening: when `gh pr merge` fails on conflict from a Done-column auto-merge attempt, the dispatcher needs to roll Status back from Done → In Code Review and label `error:merge-conflict`. Without typing, the failure is swallowed and the ticket sits "Done" forever with the PR unmerged. `MergeResult = { merged: true } | { merged: false, reason: "conflict" | "other", error }`.
- **The conflict path is the ONLY place this file deviates from "errors propagate verbatim."** All other methods (`initialize`, `createPr`, `enableAutoMerge`, private `resolvePrNodeId`) follow #19/#37 — no try/catch, no fallback retry, no message rewriting. The asymmetry is deliberate; tests pin both halves (`createPr` HTTP 500 THROWS; `mergePr` HTTP 500 returns `reason: "other"`).
- **The try/catch wraps the entire `mergePr` body, not just the mutation.** Resolution failures (PR not found by number) also surface as `{ merged: false, reason: "other", error }`. One method, one return contract — strict reading of the AC ("`mergePr` returns `{ merged: false, ... }` on failure"). The substring classifier doesn't misroute "Pull request not found" as conflict because that message lacks any conflict tokens.
- **Substring classification is lowercase + conservative.** Matches `"not mergeable"` (canonical GraphQL `mergePullRequest` failure message), `"merge conflict"`, and bare `"conflict"`. Belt-and-suspenders against minor wording variations. Test pins the lowercase normalization with an uppercase fixture.
- **Substring-match over a pre-flight `mergeable` query.** A pre-flight `pullRequest(number:N){mergeable}` adds a round-trip on every successful merge — the hot path. Substring-match keeps the happy path at one resolve + one mutate. The fragility against GitHub message drift is intentional: a drift fails a test in CI, not in production.
- **GraphQL throughout, not REST + GraphQL hybrid.** Three constraints force GraphQL: `enablePullRequestAutoMerge` is GraphQL-only (no REST endpoint exists), PR node IDs come natively from `createPullRequest`, and #19's factory pattern fits cleanly. Mixing transports would double the DI surface and the test-mock surface. The cost is a number→nodeId resolve round-trip in `enableAutoMerge`/`mergePr`.
- **`createPr`'s `draft` is a required-with-default `Boolean!` on the wire.** The mutation always sends `true` or `false`; defaulting via `?? false` happens before the variable is built, so the wire shape is predictable. Tests deep-equals `t.calls[1]?.variables` to lock body-shape including `draft`, AND separately pin `headRefName === input.head` / `baseRefName === input.base` (head/base must NOT swap — same role-mapping defense as #37's `issueId/blockingIssueId`).
- **Per-call, one-shot semantics.** `mergePr` does NOT retry across cycles. The cross-cycle `merge-attempt:N` retry counter is the loop layer's concern — this module is one shot, typed result, no internal retry, no internal cycle counter.
- **`enableAutoMerge` does NOT type conflicts.** Enabling auto-merge succeeds even when the PR is currently conflicting (GitHub queues the merge until mergeable). Conflict is `mergePr`'s scope, not `enableAutoMerge`'s.
- **No `enableAutoMerge` skip-when-already-enabled, no `mergePr(prNumber, opts?: { nodeId? })` overload, no `closePr` / `reopenPr` / `getPr` helpers, no `@octokit/graphql` dep.** Same posture as #19 / #35 / #36 / #37 — defer until an observed consumer needs the shape.

### src/pipeline/ find-ready-pr (#42)

- `src/pipeline/find-ready-pr.ts` lands the pure `findReadyPrNumber(prs): number | null` predicate. Consumers (loop's `runAutoMerge`) hand it a list of PR candidates from a future `src/github/` list-query; "ready" means not a draft AND no `error:*`-prefixed label; lowest surviving PR number wins. Empty input → `null`.
- **`ReadyPrCandidate extends PrInfo` is the type-only seam to `src/github/pr.ts`.** AC bans value imports from `src/github/`; `import type { PrInfo }` is erased at compile time and is the one allowed crossing. The `extends` shape lets the future list-PRs query return `ReadyPrCandidate[]` (or a structural superset) and have this predicate consume it without further work — alternatives considered (fully local input type / widening `PrInfo` itself) either disconnect the seam or drag cross-ticket scope.
- **The 2×2 (isDraft × errorLabeled) variant grid IS the predicate-completeness audit.** Audit comment lives at the top of `test/pipeline/find-ready-pr.test.ts`; four `it` rows tagged `// audit: row A` … `// audit: row D` sit inside the matching `describe` block. A future filter rule adds a dimension to the grid, not a special case in the predicate. The 2026-05-03 lesson (draft PR with `ready:code-review` selected for auto-merge) is captured by row B (`isDraft=true, labels=[]` → null).
- **`hasErrorLabel` uses `startsWith("error:")`** — same closed-prefix shape as `hasWipLabel` (#30) and `hasNeedsReworkLabel` (#6). Bare `error:` (empty suffix) IS filtered; if a future `error:*`-prefixed label is NOT a global block, an exclusion list lands then. Regression-tested: `something-error:foo` is NOT filtered (prefix, not substring).
- **Single-pass `< lowest` min-tracking, not `[...prs].sort()[0]`.** Same code-shape as `selectDispatches`'s early-`break`. Three explicit input-order independence test rows pin determinism — one `it` per ordering so a regression to "first-pass" or "last-pass" surfaces at the offending row.
- **Test fixture helper `mkPr(number, isDraft, labels?)` lives in the test file.** Five fields per row (incl. `nodeId`/`url` stubs to satisfy `extends PrInfo`) crowd out the predicate's actual concerns; helper threshold from the spec is 4+ fields per row. Promoted to a shared `test/_helpers/` module only when a second test file needs the same shape.
- **No defensive `?? []` on `pr.labels`, no runtime validation against `PrInfo`.** TypeScript types are the contract. Predicate reads only `number`, `isDraft`, `labels`; `nodeId`/`url` are caller-supplied passthrough this module never inspects. Same posture as `blockers.ts` and `selection.ts`.
